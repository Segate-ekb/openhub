# Как развернуть свой хаб

От пустой машины до первой опубликованной версии. Займёт минут пятнадцать.

Нужен **OneScript 2.2+**. Внешних служб — базы, S3, почтового сервера — на этом пути
не понадобится: хаб поднимется на файловой базе рядом с собой.

---

## 1. Поставить хаб

```bash
opm install openhub
```

`opm` притащит хаб и все его зависимости и положит в `PATH` команду `openhub`.

Команда берёт настройки и складывает данные **в текущем каталоге**, поэтому хаб живёт
там, откуда его запустили. Заведите ему каталог:

```bash
mkdir ~/openhub && cd ~/openhub
```

> Второй способ — контейнером: `docker run -d -p 3333:3333 -v openhub-data:/var/lib/openhub segateekb/openhub`.
> Тогда шаг с файлом настроек можно пропустить: образ уже настроен на SQLite и файловое
> хранилище на томе. Подробности — [docker/README.md](../docker/README.md).
>
> Третий — готовым комплектом для сервера: каталог [deploy/](../deploy) поднимает хаб
> и PostgreSQL одной командой `docker compose up -d`; настройки лежат в
> `autumn-properties.json` рядом, база и секреты — в секции `environment`.

## 2. Написать файл настроек

Положите рядом `autumn-properties.json`. Вот минимальный рабочий файл: SQLite и файловое
хранилище, и то и другое — в подкаталоге `./data`.

```json
{
    "winow": { "Порт": 3333 },
    "data": {
        "ИсточникиДанных": {
            "ТипКоннектора": "КоннекторSQLite",
            "СтрокаСоединения": "Data Source=./data/openhub.db"
        }
    },
    "oshub": {
        "storage": { "root": "./data" },
        "pools": { "default": "public" }
    }
}
```

Что здесь что:

| Ключ | Назначение |
| --- | --- |
| `winow.Порт` | порт HTTP-сервера |
| `data.ИсточникиДанных` | база: коннектор и строка соединения |
| `oshub.storage.root` | каталог данных: файлы пакетов и `аудит.log` |
| `oshub.pools.default` | имя основного пула — того, что отвечает на короткие адреса |

Схему хаб создаст сам при первом старте: миграций в проекте нет, накатывать нечего.

**В файл кладут только то, что нужно до подключения к базе** — порт, базу, хранилище.
Всё остальное (режим регистрации, провайдеры входа, квоты, сроки токенов, поведение
прокси) настраивается **в веб-интерфейсе** и хранится в базе. Значение, заданное файлом,
в интерфейсе показывается как «задано конфигурацией» и не редактируется — так видно,
почему поле не поддаётся.

**Секреты в этот файл не пишут.** Пароли, ключи S3 и клиентские секреты OIDC передаются
переменными окружения или файлами-секретами.

### Другая база

Хаб работает через ORM и к конкретной СУБД не привязан:

| Коннектор | Строка соединения | Когда |
| --- | --- | --- |
| `КоннекторSQLite` | `Data Source=./data/openhub.db` | личный, командный и небольшой корпоративный хаб |
| `КоннекторPostgreSQL` | `Host=db;Username=openhub;Password=…;Database=openhub;` | нагруженная инсталляция, несколько процессов хаба |
| `КоннекторJSON` | `./data/entities` | каталог JSON-файлов, вообще без СУБД: разработка, пробы, демо |

MySQL в этом ряду нет: коннектора к ней в `entity` не существует — драйвер в пакете `sql`
лежит, а коннектора поверх него никто не написал.

### Переменные окружения

Любая настройка задаётся и файлом, и переменной окружения. Порядок один для всех
ключей: **переменная окружения → файл настроек → умолчание хаба**. Ключ, записанный
в файле, переменную не отменяет — даже пустой. Обратное тоже верно: пустая переменная
(`OSHUB_POOLS_DEFAULT=`) не задаёт ничего, и значение из файла ею не погасить — процесс
не отличает пустую переменную от снятой. Чтобы сбросить настройку, уберите её из файла.

**Правило имён одно.** Имя переменной выводится из ключа настройки: подчёркивание внутри
слова удваивается, точка становится подчёркиванием, буквы — заглавными.

| Ключ | Переменная |
| --- | --- |
| `oshub.storage.root` | `OSHUB_STORAGE_ROOT` |
| `oshub.pools.default` | `OSHUB_POOLS_DEFAULT` |
| `oshub.admin.password_file` | `OSHUB_ADMIN_PASSWORD__FILE` |
| `oshub.instance.trusted_proxies` | `OSHUB_INSTANCE_TRUSTED__PROXIES` |
| `otel.exporter.otlp.endpoint` | `OTEL_EXPORTER_OTLP_ENDPOINT` |

Одинарное подчёркивание там, где нужно двойное, молча уводит значение в несуществующую
настройку: `OSHUB_ADMIN_PASSWORD_FILE` читается как `oshub.admin.password.file`.
Какое имя у какой настройки, показывает и сам хаб — на карточке настройки в
`/hub/settings` и в поле `env` ответа `GET /api/v1/hub/settings`.

**Псевдонимы.** Некоторые ключи из командной оболочки не набрать: в них кириллица, дефис,
или библиотека читает их целым узлом. Для них — и только для них — у хаба есть короткие
имена. Список закрыт:

| Переменная | Что задаёт | Почему нужна |
| --- | --- | --- |
| `OSHUB_PORT` | `winow.Порт` | кириллица в ключе |
| `OSHUB_DB_CONNECTOR` | `data.ИсточникиДанных.ТипКоннектора` | кириллица; узел базы читается целиком |
| `OSHUB_DB_CONNECTION` | `data.ИсточникиДанных.СтрокаСоединения` | то же |
| `OSHUB_DB_POOL_SIZE` | `data.ИсточникиДанных.РазмерПула` — предел соединений с базой | то же |
| `OSHUB_LOG_LEVEL` | уровень корневого журнала (`logos.logger`) | журнал настраивается узлом |
| `OSHUB_LOG_LEVELS` | уровни отдельных журналов, `Имя=Уровень,Имя2=Уровень` | то же |
| `OTEL_ENTITY_QUERY_TEXT` | `otel.entity.query-text` | дефис в ключе |
| `OSHUB_CACHE_ARTIFACTS_DIR` | `cache.артефакты.Каталог` | кириллица |
| `OSHUB_CACHE_ARTIFACTS_LIMIT__BYTES` | `cache.артефакты.Предел` | кириллица |
| `OSHUB_CACHE_MEMORY_LIMIT__BYTES` | `cache.ПределПамяти` | кириллица |
| `OSHUB_CACHE_MEMORY_TTL__SEC` | `cache.<кэш>.СрокЖизни` всех кэшей чтений из базы | кириллица; одно значение на все |
| `OSHUB_OPENAPI_ENABLED` | `winow.openapi.Включено` — описание API, `true` либо `false` | кириллица в ключе |

**Кто сильнее, псевдоним или родное имя.** Сначала решает источник, потом имя: переменная
окружения сильнее файла, а внутри одного источника родное имя сильнее псевдонима. То есть
`OSHUB_PORT` перебивает `winow.Порт` из файла; `oshub.port` из файла действует, только если
`winow.Порт` в файле нет; родное имя из окружения сильнее всего. У журнала так же:
`OSHUB_LOG_LEVEL` и `OSHUB_LOG_LEVELS` перебивают узел `logos.logger` из файла, а
`oshub.log.level` и `oshub.log.levels` из файла действуют только там, где узел журналу уровня
не назвал. Docker и Kubernetes умеют
и такие имена, которых оболочка не пропускает: `env 'OTEL_ENTITY_QUERY-TEXT=true'` — родная
форма ключа `otel.entity.query-text`.

**Узел базы** собирается лист к листу — и коннектор со строкой соединения тоже. Переменная
окружения сильнее файла по каждому листу отдельно: родные имена autumn-data
(`data_ИсточникиДанных_ТипКоннектора`, `data_ИсточникиДанных_РазмерПула` и любой другой лист)
и псевдонимы `OSHUB_DB_*` ложатся поверх одноимённых листьев файла, остальные листья файла
остаются. Поэтому несекретное держат в файле, а строку соединения с паролем — в переменной:

```json
{ "data": { "ИсточникиДанных": { "ТипКоннектора": "КоннекторPostgreSQL" } } }
```

```bash
OSHUB_DB_CONNECTION='Host=db;Username=openhub;Password=…;Database=openhub;'
```

В контейнере так не выйдет: образ сам зашивает `OSHUB_DB_CONNECTOR=КоннекторSQLite`,
а переменная сильнее файла, — там коннектор задают переменной вместе со строкой
([docker/README.md](../docker/README.md)).

Внутри окружения родные имена сильнее псевдонимов, причём для пары целиком: назвали родным
именем коннектор или строку соединения — `OSHUB_DB_CONNECTOR` и `OSHUB_DB_CONNECTION`
из окружения не берутся вовсе. Так родной коннектор оператора не склеится со строкой SQLite,
которую зашивает образ. `OSHUB_DB_POOL_SIZE` от пары не зависит. Недостающее хаб
достраивает сам: коннектор по умолчанию — `КоннекторJSON`, файловой базе — каталог `entities`
в корне данных.

С узлом, на котором база не поднимется, хаб не стартует и объясняет почему — называя, откуда
пришёл каждый лист пары (переменная, ключ файла или умолчание хаба), но не повторяя саму
строку соединения:

- коннектору, которому нужна строка соединения (PostgreSQL, SQLite), строки не досталось;
- строка соединения похожа на строку СУБД (`Host=…;Password=…`), а коннектор файловый.
  Коннектор не задан нигде — значит, он забыт, и хаб просит его задать: без отказа строка
  с паролем стала бы именем каталога файловой базы. Коннектор задан — чаще всего это
  `КоннекторJSON` проектного `autumn-properties.json` при запуске из корня репозитория и строка
  PostgreSQL из переменной, — и хаб советует задать коннектор СУБД либо путь каталога файловой
  базы строкой соединения. Признак — пары `ключ=значение` через `;` либо известный ключ СУБД первым,
  поэтому каталог файловой базы, в пути которого есть и `=`, и `;`, тоже будет отвергнут:
  такой каталог придётся переименовать;
- у нефайлового коннектора строка без единой пары `ключ=значение` — например, коннектор
  PostgreSQL из переменной и каталог `./data/entities` из файла настроек;
- узел `data.ИсточникиДанных` в файле записан значением, а не объектом с листьями.

Если коннектор и строка соединения пришли из разных источников, хаб на старте пишет об этом
строку уровня ИНФОРМАЦИЯ — без значения строки: так видно, как собран узел.

**Секреты — значением или файлом.** У настройки-секрета есть парная `…_file` — путь к
файлу, который монтируют Docker и Kubernetes: `OSHUB_ADMIN_PASSWORD__FILE`,
`OSHUB_STORAGE_S3_ACCESS__KEY__FILE`, `OSHUB_STORAGE_S3_SECRET__KEY__FILE`. Значение
сильнее файла, перевод строки в конце файла отбрасывается.

**Провайдеры входа** объявляются узлом `oshub.oidc`: список `OSHUB_OIDC_PROVIDERS=keycloak,github`
и поля каждого — `OSHUB_OIDC_KEYCLOAK_ISSUER`, `OSHUB_OIDC_KEYCLOAK_CLIENT__ID`,
`OSHUB_OIDC_KEYCLOAK_CLIENT__SECRET`, `OSHUB_OIDC_KEYCLOAK_REDIRECT__URI` и так далее
(подробно — [вход через провайдера](вход-через-провайдера.md)). Идентификатор провайдера
в имени переменной подчиняется тому же правилу: подчёркивание — удвоением, а дефис
из оболочки не набрать вовсе, только из Docker и Kubernetes.

## 3. Запустить

```bash
openhub
```

Хаб пишет в журнал ход старта и открывает порт **последним** — до строки
`Стартовые задачи завершены — открываю порт` соединение отклоняется. Готовность
спрашивают у `/ready`, живость — у `/health`.

## 4. Завести первого администратора

Пользователей в базе нет, и хаб включает режим онбординга: любая публичная страница
уводит на **`/setup`**.

![Мастер первого запуска](screenshots/setup.png)

Придумайте логин и пароль. Логин потом не сменить — он и есть имя вашего личного
пространства.

![Заполненный мастер первого запуска](screenshots/setup-filled.png)

Как только администратор появился, мастер закрывается **навсегда**: второй раз `/setup`
не откроется никому.

### Развёртывание без рук

Если хаб разворачивает не человек, а плейбук, мастер можно пропустить:

```bash
OSHUB_ADMIN_LOGIN=admin OSHUB_ADMIN_PASSWORD__FILE=/run/secrets/openhub_admin openhub
```

Администратор создаётся при старте с требованием сменить пароль при первом входе.
`OSHUB_ADMIN_PASSWORD` со значением тоже работает, но файл-секрет безопаснее: значение
переменной видно в списке процессов.

## 5. Пройти проводник первой публикации

Сразу после мастера хаб приводит вас на `/tour` — четыре шага от свежей инсталляции
до версии в каталоге. Проводник не рассказывает, а **проверяет**: отмечает шаг, когда тот
действительно сделан.

![Проводник первой публикации](screenshots/tour.png)

Первый шаг уже зелёный — администратор есть. Второй тоже: вместе с учёткой завелось
ваше личное пространство, и публиковать можно прямо в него. Но для команды нужен
общий пул.

## 6. Завести первый пул

Пакеты публикуются не «в хаб», а в конкретный пул, поэтому на свежем хабе пулов нет.

![Пулов ещё нет](screenshots/pools-empty.png)

Зайдите в **Настройки хаба → Пулы** и нажмите «Создать пул».

![Заведение пула](screenshots/pool-create.png)

Страница пула живёт под `/pools`: пакет `veles-core` в пуле `public` будет жить по
`/pools/public/packages/veles-core`, а сам пул — по `/pools/public`. Имя пула ни с одним адресом
хаба не соревнуется, поэтому годится любое допустимое. Пул с именем из `oshub.pools.default`
становится **основным** —
на него начинают отвечать короткие адреса `/download` и `/push`, ради которых и написано
большинство старых `opm.cfg`.

Квота `-1` означает «как в хабе», `0` — без ограничения. Видимость и право публикации
переключаются потом, в настройках самого пула.

## 7. Выпустить токен и опубликовать пакет

Вход по паролю нужен браузеру; `opm` ходит по токену.

Проще всего — из командной строки:

```bash
opm login localhost:3333/public --browser
```

Хаб покажет короткий код, вы подтвердите вход в кабинете — `opm` получит токен и сам
пропишет сервер в `opm.cfg`.

Токен можно выпустить и руками, в кабинете: **Настройки аккаунта → Токены доступа**.
У токена задаются имя (чтобы потом вспомнить, зачем он), права — `read` или `read,write` —
и срок: от 1 до 365 дней, бессрочных хаб не выпускает. Значение показывается **один раз**,
при выпуске; токенов может быть несколько, и каждый отзывается отдельно.

Токен никогда не даёт больше, чем есть у его владельца, — и токену для конвейера ни к чему
уметь всё, что умеете вы: выпустите отдельный, только на запись в один пул.

![Токены доступа](screenshots/tokens.png)

Дальше всё как обычно:

```bash
opm build .
opm push --hub localhost:3333/public мойпакет-1.0.0.ospx
opm install localhost:3333/public/мойпакет
```

Адресную форму команд понимает `opm` с изменениями под новый хаб
([oscript-library/opm#275](https://github.com/oscript-library/opm/pull/275)); в выпущенном `opm`
её пока нет. Выпущенный клиент подключается записью в `opm.cfg` — готовую запись со всеми путями
хаб печатает прямо на странице пакета, остаётся скопировать.

Опубликованная версия сразу видна в каталоге — с описанием из README пакета, версиями,
зависимостями и готовой командой установки.

![Карточка пакета](screenshots/package.png)

## Что настроить дальше

**Внешний адрес инсталляции.** Настройки хаба → Базовые настройки → «URL инстанса».
Из него хаб считает адрес возврата для провайдеров входа и аудиторию доверенной
публикации; пока он пуст, ни то ни другое не заработает.

**Хаб, который opm знает по умолчанию.** Настройки хаба → Базовые настройки → «opm знает
этот хаб по умолчанию». Включают её там, где `opm` ходит без всякой настройки клиента
(`hub.oscript.io`): у пакетов основного публичного пула со страницы пропадает карточка
«Установка через запись в opm.cfg», а с главной — образец `opm.cfg`. Подсказки публикации —
пустая главная, шаги «Выпустить токен публикации» и «Опубликовать первую версию» и карточка
«Публикация из opm» в проводнике — для основного пула тоже не просят прописывать хаб:
`opm push` без настройки публикует именно в него. Токен и канал тогда передаются опциями —
`opm push --token <токен> -c stable мойпакет-1.0.0.ospx`: без `opm.cfg` канал сам `opm`
определяет только в git-репозитории на ветке `master`. Пакетам других пулов запись
в `opm.cfg` по-прежнему нужна, и подсказка у них остаётся.

**Прокси для уведомлений в Telegram.** Настройки хаба → «Подписки на события» →
блок «Доставка уведомлений»: сервер, порт, пользователь и пароль прокси, через который хаб
обращается к `api.telegram.org`. Пустой сервер означает «ходить напрямую» — так хаб и вёл
себя раньше. Правка действует сразу, перезапуск не нужен. Что важно знать:

- прокси обязан быть **HTTP-прокси с методом `CONNECT`** (squid, 3proxy, tinyproxy и им
  подобные). SOCKS-прокси платформа OneScript не поддерживает, и адрес вида `socks5://…`
  работать не будет;
- прокси действует **только** на уведомления Telegram. На вебхуки, источники пулов,
  зеркала, почту и объектное хранилище он не распространяется: туда хаб ходит напрямую,
  и отдельной настройки прокси у них нет;
- сколько ждать ответа одной отправки, задаёт `oshub.webhooks.delivery_timeout_sec`
  (10 секунд, ключ конфигурации инсталляции). Медленному прокси его поднимают там же,
  где остальные настройки развёртывания;
- пароль прокси — секрет: поле открывается пустым, значение не показывается ни на экране,
  ни в API настроек, ни в журнале, ни в тексте отказа доставки. Пустое поле означает
  «оставить как есть», стирает значение кнопка сброса;
- недоступный прокси — обычный отказ доставки: причина видна в карточке подписки и в
  журнале, задание повторяется по общим правилам подписок.

**Подробность журнала — с экрана «Логи».** Настройки хаба → «Логи» (`/hub/settings/logs`,
только администратору хаба). Уровень любого лога хаба и библиотек меняется здесь без
перезапуска, а вкладка «Строки» показывает последние строки журнала прямо на экране. Что
важно знать:

- правка действует сразу и **до перезапуска**: в базу она не пишется, после перезапуска
  уровни снова берутся из `OSHUB_LOG_LEVEL`, `OSHUB_LOG_LEVELS` и файла настроек, а отправка
  в коллектор — из `OSHUB_LOG_OTEL_LEVELS`. Чтобы оставить заданное, экран печатает в блоке
  «Закрепить» готовые строки этих переменных — их переносят в окружение развёртывания.
  Колонка «Откуда» у каждого лога называет, откуда его уровень: окружение, файл настроек,
  умолчание, корень или экран — тогда кто и когда;
- каждая правка уровня и отправки пишется в журнал аудита: кто, когда и с какого адреса;
- искать логи по имени класса не обязательно. **Пути** — «выдача пакета», «поход к чужому
  хабу», «приём внешней версии», «публикация», «вход», «очередь уведомлений», «хранилище
  артефактов» — сужают дерево до логов, которые участвуют в этом деле, в каком бы модуле
  они ни жили, а «Всем под отбором» задаёт им один уровень разом. Поиск ищет подстроку
  и в имени лога, и в имени ветки;
- дерево — модули хаба и библиотеки по веткам. Свёрнутая ветка показывает итоги: сколько
  в ней логов, сколько строк они пишут в минуту, сколько пишут отладку, сколько задано
  с экрана, сколько не уходит в коллектор. Раскрывает ветку кнопка с её именем: страница
  открывается у раскрытой ветки, а адрес запоминает раскрытые ветки — ссылка и «назад» в браузере
  показывают дерево таким же. Выбранное в дереве, но ещё не применённое, при раскрытии
  не теряется, сколько бы логов ни выбрали: оно
  помечено «не применено», названо числом сверху и ждёт «Применить», а «Отменить» его
  сбрасывает; Enter в поле дерева — то же «Применить». Выбранное не попадает в адрес страницы:
  ссылкой передаётся экран, но не чужой выбор. Уровень ветки — это правка всех её логов разом, своего уровня у ветки нет; лог,
  которому в той же отправке выбрали свой уровень, получает свой. «Как при старте» снимает
  с лога всё заданное с экрана — и уровень, и отправку. После «Применить» страница открывается
  у ветки, которую правили, и называет логи, которые правка действительно изменила; уровень,
  который у лога уже свой, выбранный ещё раз, — «ничего не изменилось». Одна отправка формы
  сначала выключает отправку и понижает уровни, а потом поднимает и включает — коллектор
  не получает всплеска отладки;
- тумблер «Коллектор» у лога и у корня решает, уходят ли их строки в OpenTelemetry. Отправку,
  выключенную настройкой, включает тот же тумблер. У лога, который до коллектора не доходит
  вовсе, тумблер заперт и подписан. Пока журнал в коллектор не уходит — выключена телеметрия
  либо экспорт логов, — тумблеры ничего не отправляют, и экран говорит об этом сверху;
- логи, которые с экрана не правятся, показаны с причиной: журнал аудита (`аудит`)
  не приглушают, а логи библиотек, заведённые раньше, чем хаб прочитал настройки, пишут без
  обезличивания, и поднимать их подробность с экрана нельзя. Групповая правка такие логи
  пропускает и называет пропущенные;
- «Строки» — последние строки, которые хаб написал, свежие сверху, время UTC. Текст строки
  ровно тот, что ушёл в консоль, — уже обезличенный. Предупреждения и ошибки хаб держит
  ещё и в отдельной памяти, которую поток отладки не вытесняет: отбор «Память → Только
  важное». Сами строки не обновляются — «Обновить» перечитывает их тем же отбором, а отбор
  живёт в адресе, и строки одного пути или лога можно дать ссылкой. Путь или ветку, которых
  в этой версии хаба нет, экран называет словами, а не показывает весь поток. От строки —
  ход к её логу в дереве, из дерева — к строкам лога или ветки;
- «Вернуть всё как при старте» снимает всё, что задано с экрана, в том числе заданное
  другим администратором, поэтому сначала показывает отдельным шагом, что снимется: какой
  лог, что задано, кем и когда, — и кнопку с числом снимаемого. Кнопка снимает ровно
  показанное: заданное кем-то уже после вопроса остаётся. Если среди снимаемого есть правки
  других администраторов, вопрос выделен и называет их. Отбор после возврата остаётся.

**База стран посетителей.** Хаб умеет определять страну запроса сам, по встроенной базе
диапазонов адресов, и в момент запроса никуда не ходит. Пока правил по стране нет, база
не читается вовсе — этот раздел нужен тем, кто такие правила заводит.

> ⚠ **Правило без базы закрывает провайдера ВСЕМ.** Посетитель, страну которого хаб
> определить не смог, считается пришедшим из закрытой страны: не проверил — отказал.
> Поэтому файл базы кладут **до** того, как повесить правило «закрыт в странах», —
> иначе вход через этого провайдера перестанет работать у всех разом. Окно «Страны
> и доступ» говорит об этом прямо и показывает состояние базы.
>
> ⚠ **За обратным прокси правило требует `OSHUB_INSTANCE_TRUSTED__PROXIES`.** Без списка
> доверенных сетей хаб считает адресом клиента адрес самого прокси: он не публичный,
> страна не определяется, и правило закрывает провайдера **всем — включая вас**. Окно
> «Страны и доступ» печатает строку «Страна вашего запроса»: если там «не определена»,
> дело почти всегда в этом списке, и правило вешать рано.

Откуда база. Это **DB-IP Lite Country** — свободный файл под лицензией
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/), учётной записи он не требует:

```bash
# каталог никто не создаёт за вас: пока обновление выключено, его некому завести
mkdir -p /var/lib/openhub/гео

# файл текущего месяца; выпуск нового появляется у издателя не первого числа
curl -sSfL -o dbip.csv.gz \
  https://download.db-ip.com/free/dbip-country-lite-2026-09.csv.gz
gunzip -c dbip.csv.gz > /var/lib/openhub/гео/dbip-country-lite.csv
```

Куда класть. По умолчанию — `<oshub.storage.root>/гео/dbip-country-lite.csv`; другой путь
задаёт `OSHUB_GEO_DB__PATH`. Хаб замечает положенный руками файл сам, по размеру и времени
изменения, и перечитывает его на ближайшем заходе задачи — перезапускать инсталляцию
не нужно.

Обновляться из сети хаб по умолчанию **не будет**: в закрытом контуре наружу ходить
нельзя, а незаметно уехавшая за файлом инсталляция — сюрприз. Кому обновление нужно:

| Переменная | Умолчание | Что делает |
| --- | --- | --- |
| `OSHUB_GEO_UPDATE_ENABLED` | `false` | разрешает ходить за новым выпуском |
| `OSHUB_GEO_UPDATE_URL` | адрес DB-IP | шаблон выпуска; `{ГОД}` и `{МЕСЯЦ}` подставляет хаб |
| `OSHUB_JOBS_GEO__UPDATE__INTERVAL__SEC` | `86400` | как часто идёт заход |
| `OSHUB_GEO_DB__PATH` | пусто | путь к файлу базы |
| `OSHUB_GEO_HEADER` | `CF-IPCountry` | заголовок страны от обратного прокси; пусто — не читать |
| `OSHUB_GEO_SOURCE__ORDER` | `база-прокси` | кого спрашивать первым; второе значение — `прокси-база` |

Неудачное обновление прежнюю базу не трогает, а причину объясняет происшествием на экране
администратора: «базы нет», «база не обновилась», «база устарела». Возраст базы виден там же.

Если перед хабом стоит обратный прокси, который страну уже знает (например, Cloudflare
с `CF-IPCountry`), хаб возьмёт её оттуда — но **только** с соединения из сетей, названных
в `OSHUB_INSTANCE_TRUSTED__PROXIES`. Заголовок с любого другого адреса снимается с запроса:
написать в него чужую страну может кто угодно.

**Порядок источников — это приоритет, и умолчание делает заголовок запасным.** Ответ базы
«адрес публичный, но не из наблюдаемых стран» — это ответ, а не молчание, поэтому при
`база-прокси` до `CF-IPCountry` очередь доходит только тогда, когда базе сказать нечего
вовсе: файла нет, индекс ни разу не построился. Инсталляции за Cloudflare, которая хочет,
чтобы решал именно заголовок, а база работала запасом, нужен `OSHUB_GEO_SOURCE__ORDER=прокси-база`.

> ⚠ **Память: около двух килобайт на диапазон, и на время перестройки индексов два.**
> Одна Россия — это 15 676 диапазонов, около 31 МБ в памяти и до 62 МБ на пике; пять стран
> (RU, BY, KZ, DE, US) — 145 тысяч диапазонов, около 345 МБ и до **666 МБ** на пике, пока
> живы прежний и новый индексы. Наблюдаете больше одной-двух стран — поднимите лимит памяти
> контейнера соответственно.

> **Атрибуция обязательна.** Лицензия CC BY 4.0 требует указать источник: страницы,
> которые пользуются результатом, несут ссылку `IP Geolocation by DB-IP` на
> <https://db-ip.com>. Замените базу своей — замените и ссылку.

**Журнал: подробность, коллектор и память.** Хаб пишет журнал в три выхода: консоль
процесса (`console`), память для просмотра на экране (`memory`) и коллектор телеметрии
(`otel`, только при `OTEL_ENABLED=true`). Сколько писать и куда, задают пять ключей:

| Переменная | Ключ | Что задаёт | Умолчание |
| --- | --- | --- | --- |
| `OSHUB_LOG_LEVEL` | `oshub.log.level` | уровень журнала целиком | `INFO` |
| `OSHUB_LOG_LEVELS` | `oshub.log.levels` | уровни отдельных журналов, `Имя=Уровень,Имя2=Уровень`; имя журнала — имя класса | — |
| `OSHUB_LOG_OTEL_LEVEL` | `oshub.log.otel.level` | с какого уровня строки уходят в коллектор; `DISABLE` — журнал в коллектор не идёт | как уровень журнала |
| `OSHUB_LOG_OTEL_LEVELS` | `oshub.log.otel.levels` | то же отдельным журналам и их потомкам по имени, `Имя=Уровень,…`; `DISABLE` — этот журнал в коллектор не идёт | — |
| `OSHUB_LOG_TAIL_SIZE` | `oshub.log.tail.size` | сколько последних строк хаб держит в памяти; `0` — не держит | `2000` |

Уровни — `DEBUG`, `INFO`, `WARN`, `ERROR`, `CRITICALERROR`, `DISABLE`, и `DEFAULT` —
«как у всех». Непонятое значение любого из пяти ключей хаб не роняет и ничего им не задаёт:
настройку берёт следующий по старшинству источник, ровно как если бы непонятого значения не
было, а на старте в журнале появляется предупреждение с ключом, переменной и перечнем
допустимых. `OSHUB_LOG_OTEL_LEVEL=ТИШЕ` при `oshub.log.otel.level: ERROR` в файле даёт порог
`ERROR`; непонятая ёмкость памяти без запасного источника — умолчание 2000.

- **Подробность поднимается точечно.** `OSHUB_LOG_LEVELS=РезолверВыдачи=DEBUG` включает
  отладку одному журналу: остальные остаются на своём уровне и отладочных строк не
  собирают вовсе — ни в консоль, ни в память, ни в коллектор.
- **Порог коллектора — слой поверх уровней и выходов.** Он меняет у журнала только выход
  в коллектор: строки уходят туда не подробнее уровня журнала и не подробнее порога, а
  уровень журнала, консоль и память порог не трогает. Поэтому он только сужает:
  `OSHUB_LOG_OTEL_LEVEL=DEBUG` при уровне `INFO` отладку в коллектор не отправит, а при
  `OSHUB_LOG_OTEL_LEVEL=WARN` в коллектор уходят только предупреждения и ошибки. Порог,
  названный журналу, действует и на его потомков по имени (`oscript.lib=ERROR` — и на
  `oscript.lib.autumn-cache`), ближайший названный выигрывает, общий — остальным. Журналу,
  которому выход в коллектор не назван, сужать нечего: порог на него не действует, а если
  журнал назван в `OSHUB_LOG_OTEL_LEVELS`, на старте об этом предупреждение. Трассы и метрики
  порог не трогает; выключить сигнал журнала целиком на стороне SDK — `OTEL_LOGS_EXPORTER=none`,
  но тогда строки всё равно отдаются мосту, а при пороге `DISABLE` мосту они не отдаются вовсе.
- **Память** держит два кольца: все строки и отдельно предупреждения с ошибками — четверть
  ёмкости, — чтобы поток отладки не вытеснял то, ради чего открыли экран. Строки в памяти
  те же, что в консоли: ящики адресов почты сняты. Память живёт до перезапуска процесса.

Поднять отладку одному компоненту и не отправлять её в коллектор:

```bash
OSHUB_LOG_LEVELS=РезолверВыдачи=DEBUG,КэшАртефактов=DEBUG
OSHUB_LOG_OTEL_LEVELS=РезолверВыдачи=INFO,КэшАртефактов=DISABLE
```

Консоль и память получают отладку обоих журналов, коллектор — сведения и ошибки
`РезолверВыдачи` и ничего от `КэшАртефактов`.

**Родные ключи logos в файле настроек.** Те же уровни можно написать узлом `logos.logger`
смонтированного `autumn-properties.json` — так, как их пишут в любом проекте на ОСени. Выходы
журналу называют логическими именами `console`, `memory`, `otel`:

```json
{
  "logos": {
    "logger": {
      "rootLogger": {"level": "INFO", "appenders": ["console", "memory", "otel"]},
      "РезолверВыдачи": "DEBUG",
      "oscript.lib": {"level": "WARN", "appenders": ["console"], "additivity": false}
    }
  }
}
```

Узел читается так, как его читает сама logos. Журнал берёт свою запись узла, а если её нет —
запись ближайшего названного предка по имени (`oscript.lib` для `oscript.lib.autumn-cache`),
и только её; чего в записи нет, берётся у корня. Выходы, названные журналу, **добавляются**
к выходам корня; заменяют их — только с `"additivity": false`, как у `oscript.lib` выше: он
пишет только в консоль.

Порядок источников — общий для всех настроек хаба (см. «Кто сильнее» выше): переменная
окружения сильнее файла, а в одном файле родной узел `logos.logger` сильнее ключей
`oshub.log.*`. Порог коллектора — ключи хаба без родной пары: переменная сильнее файла.
С узлом он не спорит, потому что ложится поверх него. Выходы корня в узле и общий порог
в том же файле работают вместе:

```json
{
  "logos": {"logger": {"rootLogger": {"level": "INFO", "appenders": ["console", "memory", "otel"]}}},
  "oshub": {"log": {"otel": {"level": "WARN"}}}
}
```

Консоль и память получают сведения, коллектор — предупреждения и ошибки. Классы способов
вывода — устройство хаба: узел `logos.appender` из файла не применяется, и хаб говорит об
этом на старте. admin-cli и сидеры читают те же уровни, но пишут только в консоль.

Журнал аудита живёт отдельно: он пишется только в файл `аудит.log` каталога данных — ни
в консоль, ни в память, ни в коллектор, — и настройки журнала его не касаются. Заглушённый
корень его не глушит, а уровень, выходы и порог, названные журналу `аудит`, не применяются
(на старте об этом предупреждение).

> Часть журналов библиотек рождается раньше, чем хаб собирает связку, и живёт на `INFO`
> с библиотечной консолью: ни уровни, ни коллектор, ни память до них не доходят. В коллектор
> и в память попадают журналы классов хаба.

**Шифрование канала — не задача хаба.** Веб-сервер принимает соединения по открытому
протоколу, настройки TLS у хаба нет и не будет. Наружу хаб выставляют **только** за
обратным прокси, который терминирует TLS; там же живут ограничение темпа и сжатие.
Сам порт хаба слушает локальный адрес или сеть контейнеров.

## Описание API

Хаб отдаёт описание своего HTTP API в формате OpenAPI 3.1. Его собирает веб-сервер winow
из разметки самих адресов, поэтому описание не отстаёт от кода:

| Адрес | Что |
| --- | --- |
| `/swagger-ui.html` | страница Swagger UI: адреса по группам, параметры, коды ответов, пробный запрос |
| `/v3/api-docs` | то же описание машиночитаемым JSON — по нему пишут клиента |
| `/v3/api-docs.yaml` | оно же в YAML |

По умолчанию описание выключено. Включает его переменная окружения — в том числе в образе
и в Kubernetes:

```bash
OSHUB_OPENAPI_ENABLED=true
```

либо ключ `winow.openapi.Включено` файла настроек. `false` либо отсутствие того и другого
выключает все три адреса:

```json
{
    "winow": { "openapi": { "Включено": true } }
}
```

Родное имя ключа, `WINOW_OPENAPI_ВКЛЮЧЕНО`, тоже действует, но кириллическое имя годится
только для `environment:` в compose: оболочка `sh -c` (dash) такую переменную молча
выбрасывает, а Kubernetes не допускает вовсе. Поэтому берите `OSHUB_OPENAPI_ENABLED`.

Паспорт описания хаб ставит сам: заголовок «OpenHub API», версию хаба, лицензию MIT и шапку
с общими правилами — как входить, как выглядит отказ, как листаются списки, чем «устарело»
отличается от «упразднено». Ключи `winow.openapi.Заголовок`, `Сводка`, `Описание`, `Версия`
и `Лицензия` в файле настроек либо в окружении его перебивают.

Что знать об описании:

- страница берёт движок Swagger UI с CDN `cdn.jsdelivr.net`: у инсталляции без выхода
  в интернет она остаётся пустой, а машиночитаемое описание отдаётся как обычно. Открытая
  не с `localhost`, страница ещё и показывает значок проверки описания, который браузер
  загружает с `validator.swagger.io`;
- программе для входа нужен ключ доступа в заголовке `Authorization: Bearer` либо
  `OAUTH-TOKEN`. Сессия веб-интерфейса годится для чтения, а изменяющий запрос по сессии хаб
  отклоняет `csrf_failed`: CSRF-токена API не выдаёт. Два исключения: выпуск и отзыв ключа
  (`/api/v1/tokens`) и выход работают по сессии без CSRF, а публикация сессию не видит вовсе
  и отвечает на неё 401. Пробный запрос со страницы уходит с кукой сессии браузера, поэтому
  чтение из неё работает, а изменение — нет: подставить ключ страница не умеет, схему входа
  по ключу winow не описывает;
- в описание попадают и адреса экранов веб-интерфейса — это HTML-страницы и формы, а не
  API. Машинные адреса разложены по группам: «Пулы», «Пакеты», «Выдача для opm»,
  «Публикация» и другие;
- у адреса, который обслуживает несколько глаголов, описание одно на все глаголы: что
  делает каждый, сказано в тексте операции.

## Пробы для оркестратора

```bash
curl http://localhost:3333/health   # живость: процесс жив
# {"status": "ok", "version": "0.4.0", "uptime_seconds": 5,
#  "database": {"status": "ok",
#               "pool": {"busy": 0, "free": 1, "waiting": 0, "created": 1, "limit": 10}}}

curl -i http://localhost:3333/ready # готовность: можно слать трафик
# 200 {"status": "ready", "ready": true, "pending": [], "database": {...}}
# 503 {"status": "starting", "pending": ["mirror.синхронизация"], "database": {...}}
# 503 {"status": "database_unavailable", "ready": false, "pending": [],
#      "database": {"status": "unavailable",
#                   "pool": {"busy": 10, "free": 0, "waiting": 3, "created": 10, "limit": 10},
#                   "reason": "пул соединений исчерпан: занято 10, свободных нет,
#                              ждут 3, мест занято 10 из 10"}}
```

Пробу готовности вешайте на `/ready`, живости — на `/health`. В теле ответа `503`
перечислены незакрытые стартовые гейты — по нему видно, чего хаб ждёт.

Обе пробы называют состояние базы разделом `database`: отвечает ли она (`status`),
снимок пула соединений и фраза `reason`, если не отвечает. Снимок — пять чисел: `busy`
(соединений у потоков), `free` (свободные), `waiting` (стоят в очереди), `created`
(занятых мест в пуле — открытые соединения плюс те, что открываются прямо сейчас;
именно это число пул сравнивает со своим размером) и `limit` (размер пула, `0` — без
предела). Снимок есть в любом ответе, включая отказ; пропадает он ровно в одном случае —
источник данных закрыт, и пула у него уже нет. Различие между адресами принципиальное:

- **`/ready` уводит инстанс из ротации**, когда база не отвечает: `status` становится
  `database_unavailable` — это не `starting`, само оно не пройдёт;
- **`/health` остаётся `200`**, пока жив процесс. Перезапуск базу не лечит, а идущий
  обход зеркала убивает, поэтому оркестратору повода перезапускать хаб проба живости
  не даёт — она только называет состояние.

Проба не встаёт в очередь за соединением: исчерпанный пул она видит по снимку и отвечает
отказом сразу, поэтому укладывается в таймаут оркестратора даже тогда, когда все запросы
хаба стоят в очереди к базе.

> **Плановый простой СУБД: хаб в это время не перезапускайте.** Проба готовности
> отказывает и на старте тоже, поэтому под, поднятый при недоступной базе, не пройдёт
> `startupProbe` (в манифестах комплекта на `/ready` отведено 300 с) — и будет убит
> и перезапущен по кругу, пока база не вернётся. Уже работающий хаб в такой ситуации
> спокойно доживёт до возвращения базы: живость по ней не отказывает. Это цена за
> «недоготовый инстанс трафика не получает», и она осознанная — но чинить простой СУБД
> перезапуском хаба не выйдет.
