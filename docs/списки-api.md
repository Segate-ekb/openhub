# Как читать списки HTTP API

Все списковые ручки `/api/v1/*` отдают **страницу** — один и тот же конверт, одни и те же
параметры, один и тот же потолок выдачи. Разбираться отдельно с каждым адресом не нужно:
что верно для зеркал пула, верно и для грантов, и для версий пакета.

Полное машиночитаемое описание API живёт по адресу `/api/v1/openapi.json` вашей
инсталляции.

---

## Форма страницы

```json
{
  "items": [ ... ],
  "page": 1,
  "pageSize": 200,
  "total": 37,
  "has_more": false
}
```

| Поле | Что значит |
| --- | --- |
| `items` | элементы этой страницы |
| `page` | номер отданной страницы, считая с единицы |
| `pageSize` | размер страницы, которым хаб воспользовался |
| `total` | сколько элементов во всём списке, а **не** на странице |
| `has_more` | за этой страницей осталось ещё |

Три ручки зовут поле со списком по-своему, и это историческое имя, которое не меняется:
`GET /api/v1/pools/{pool}/packages/{name}/versions` отдаёт список в поле `versions`,
`GET /api/v1/pools/{pool}/packages/{name}/tags` — в поле `tags`, `GET /api/v1/tokens` —
в поле `tokens`. Остальные поля страницы у них те же самые.

---

## Как листать

Два параметра запроса, оба необязательные:

- `page` — номер страницы, считая с единицы;
- `pageSize` — сколько элементов взять.

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "$HUB/api/v1/pools/corp/mirrors?pageSize=20&page=2"
```

Номер за краем списка — не ошибка: страница приезжает пустой, а `total` по-прежнему
называет весь список. Непонятное значение параметра тоже не отказ: номером становится
первая страница, размером — умолчание ручки.

---

## Потолок выдачи

**В одном ответе хаб отдаёт не больше потолка выдачи** — по умолчанию 200 элементов.
Запросили `pageSize=100000` — получите потолок, и `pageSize` в ответе честно назовёт то
число, которым хаб воспользовался.

Потолок — предохранитель инсталляции, а не свойство протокола: администратор задаёт его
настройкой `oshub.api.page_max` в файле настроек хаба (или переменной окружения
`OSHUB_API_PAGE__MAX`). Рядом живёт `oshub.api.page_size` — размер страницы по умолчанию
у ручек, которые листают: каталог пакетов пула, поиск, пулы и группы.

Потолок теперь один на весь API. Раньше у четырёх листающихся ручек он был **100**;
с общим потолком они отдают до **200** элементов на странице, если попросить
`pageSize=200`. Запрос без параметров у них не изменился: та же первая страница
размером `oshub.api.page_size`.

---

## Запрос без параметров

Ручка, которая **листается** — `/api/v1/pools`, `/api/v1/pools/{pool}/packages`,
`/api/v1/search`, `/api/v1/groups`, — без параметров отдаёт первую страницу размером
`oshub.api.page_size` (по умолчанию 20).

Все остальные списковые ручки без параметров отдают **список целиком**, как отдавали
раньше: страница у них во весь потолок выдачи. Список длиннее потолка обрезается, и тогда
`has_more` равен `true` — молчаливого усечения не бывает. Скрипт, который читает `items`
и `total` и не знает ни про какие страницы, продолжает работать; чтобы убедиться, что он
видит всё, достаточно проверить `has_more`.

---

## Что страницами не отдаётся

- **Выдача для `opm`** — `/pools/{pool}/download/list.txt` и адреса артефактов. Это
  контракт клиента `opm`, и он не меняется: `list.txt` был и остаётся плоским списком имён
  в `text/plain`.
- **Срез изменений** `/api/v1/pools/{pool}/changes` — у него своя, курсорная порционность:
  `since`, `cursor` и `limit`, а в ответе `as_of`, `next_cursor` и `has_more`. Так его
  читает зеркало соседнего хаба, идя инкрементом; подробности — в статье
  [Как настроить кэширующий прокси](кэширующий-прокси.md).
