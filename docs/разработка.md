# Разработка

Как поднять хаб из исходников, где что лежит и как прогнать тесты.

## Собрать и запустить

Нужен **OneScript 2.2.1** и старше: на более раннем `opm install` не ставит ни хаб, ни `winow`.
Дистрибутив несёт `opm`, отдельно ставить его не требуется.

Зависимости ставятся из двух пулов hub.oscript.io, прописанных в [`opm.cfg`](../opm.cfg) корня
репозитория: сначала основной, за ним `segate-ekb`. opm берёт пакет из первого пула, где нашлась
нужная версия, поэтому из `segate-ekb` приезжает только то, чего нет в основном: `oint` 2.4.0.1
(клиент S3: подпись, загрузка частями, скачивание прямо в файл) — ветка `сборка-segate-ekb`
форка [Segate-ekb/OpenIntegrations](https://github.com/Segate-ekb/OpenIntegrations).

```bash
opm install -l --dev  # зависимости из packagedef в ./oscript_modules
oscript src/main.os   # хаб на http://localhost:3333
```

`opm install -l` запускают из корня репозитория. opm берёт первый найденный `opm.cfg`, начиная
с текущего каталога, — здесь это проектный, `~/.opm.cfg` в корне репозитория не действует.

Из корня репозитория хаб читает проектный [`autumn-properties.json`](../autumn-properties.json):
база `КоннекторJSON` в `./data/entities`, данные в `./data`, описание API включено, телеметрия
выключена. Остальное — [справочник настроек](настройки.md).

## Где что лежит

| Путь | Что в нём |
| --- | --- |
| `src/main.os` | точка входа: загрузка настроек, сборка контейнера ОСени, запуск winow |
| `src/модули/` | модули хаба, по одному каталогу на предмет; классы — в `Классы/` модуля |
| `src/статика/` | стили, скрипт и знак хаба, которые отдаются браузеру |
| `tests/` | наборы OneUnit (`*_Тесты.os`) по модулям; раскладка — в разделе «Тесты» |
| `scripts/` | `смоук.sh` и `тесты.sh`, их общая шапка прогона `шапка-прогона.sh`; `admin-cli.os` — `create-admin` для первого администратора и восстановления доступа; сидеры интеграционных тестов |
| `tools/` | демо-стенд; `ПоставкаЗависимостей.os` — отбор зависимостей в пакет `.ospx` |
| `docker/`, `deploy/` | образ, тестовый стенд, комплект для сервера |
| `docs/` | статьи |

Классы модулей — желуди [ОСени](https://github.com/autumn-library/autumn): зависимости
внедряются контейнером (`&Пластилин`), а не создаются руками. База — только через
[autumn-data](https://github.com/autumn-library/autumn-data): одна таблица — сущность и класс
`Хранилище*` в модуле своего предмета (учётки — во `вход`, пакеты и пулы — в `реестр`);
в модуле `данные` — только общая техника доступа.

## Тесты

Тесты — [OneUnit](https://github.com/oscript-library/oneunit). Наборы разложены по модулям: правка
модуля проверяется его наборами, а не прогоном всего дерева.

| Каталог | Что в нём |
| --- | --- |
| `tests/<модуль>/` | наборы, чей предмет — этот модуль, в том числе собранный в контейнер с соседями |
| `tests/<модуль>/фикстуры/` | фикстуры, нужные только наборам модуля |
| `tests/e2e/<модуль>/` | наборы, поднимающие живой хаб, — по модулю, чьё поведение они проверяют |
| `tests/сквозные/` | линты всего дерева и глобальные инварианты: имена классов и прозвища, каталог событий, журнал, поставка |
| `tests/инфраструктура/` | самотесты фикстур, стендов засева и обвязки тестов |
| `tests/внешние/` | наборы, которым нужна внешняя система: MinIO, PostgreSQL, живой hub.oscript.io |
| `tests/фикстуры/` | общие фикстуры и их данные |
| `tests/инструменты/` | сценарии обвязки прогона: подъём и остановка общих хабов групп |

```bash
opm install oneunit@0.4.1                    # один раз
scripts/смоук.sh                             # минимум по назначению хаба, ~1 минута
scripts/тесты.sh реестр                      # наборы модуля — перед коммитом шага
scripts/тесты.sh реестр --сквозные           # плюс линты tests/сквозные/ — один раз в конце шага
scripts/тесты.sh реестр --с-потребителями    # плюс наборы других модулей, которые грузят код модуля
scripts/тесты.sh реестр --e2e                # плюс живые наборы модуля
scripts/тесты.sh реестр --список             # только показать, что попадёт в прогон и почему
scripts/тесты.sh --e2e                       # все живые наборы
scripts/тесты.sh --всё                       # регрессия: всё дерево, кроме внешних наборов
scripts/тесты.sh --внешние                   # внешние наборы: нужны поднятые MinIO и PostgreSQL
scripts/тесты.sh --инфраструктура            # самотесты фикстур, стендов и обвязки тестов
scripts/тесты.sh --плавающие                 # карантин: тесты, которые плавают под нагрузкой
scripts/тесты.sh --всё --параллельно 4       # регрессия: четыре корзины и корзина «хабы»
scripts/тесты.sh --всё --параллельно 3 --веса scripts/время-наборов-ci.tsv  # корзины по таблице CI
scripts/тесты.sh реестр --время              # наборы по одному и таблица «набор — секунды»
scripts/тесты.sh --всё --время --таблица-времени scripts/время-наборов.tsv  # таблица весов корзин
oneunit execute -f tests/реестр/Теги_Тесты.os  # один набор
```

Прогон модуля берёт только его наборы. Линты `tests/сквозные/` читают всё дерево и идут долго, их
добавляет ключ `--сквозные`; он сочетается с `--с-потребителями`, `--e2e`, `--параллельно` и `--список`.
Регрессия `--всё` сквозные наборы содержит.

`--параллельно N` (без ключа прогон идёт одним `oneunit`) делит отобранные наборы на N корзин,
выравнивая их суммарный вес, и запускает каждую своим `oneunit execute` в своём временном
воркспейсе git с копией `oscript_modules`: процессы одного чекаута мешают друг другу читать общие
файлы. Воркспейсы стоят на снимке рабочего дерева, поэтому корзины гоняют ровно то, что в дереве, —
с правками и новыми файлами, как и прогон одним `oneunit`. Каждая корзина — своя группа процессов:
прерванный прогон гасит корзины вместе с поднятыми ими хабами, печатает хвосты их журналов и только
потом снимает воркспейсы. Состав корзин печатается до запуска строками `== корзина K/N: <набор>`,
вывод корзины — строками с префиксом `корзина K │`: первой — по ходу прогона, остальных — по их
окончании. Ключи файлов отчёта oneunit после `--` (`--junit`, `--genericExecution`, `--openTestReport`,
`--genericCoverage`, `--cobertura`) корзины не принимают — код 2: все корзины писали бы в один файл,
отчёт снимают прогоном в один поток. В конце — `== СВОДКА`: суммы строк статистики
oneunit по всем корзинам и «Тестирование завершилось удачно», только если так закончила каждая
корзина; код выхода ненулевой, если ненулевой у любой. Порты и временные каталоги наборы берут
через `ВыдачаПортов` и `УникальныеИмена`, поэтому корзины друг другу не мешают.

Вес набора — его время из таблицы `scripts/время-наборов.tsv` (строки `<секунды><TAB><набор>`, путь
набора — как в `-f`, по пути по порядку); набору, которого в таблице нет, — медиана таблицы; без
таблицы — размер файла. `--веса <файл>` (только вместе с `--параллельно`, файл обязан быть, иначе
код 2; путь — от каталога вызова) берёт веса из другой таблицы того же формата. Таблиц две: маковская
`scripts/время-наборов.tsv` — умолчание, и `scripts/время-наборов-ci.tsv` — время наборов на раннере
GitHub Actions, где живые наборы под нагрузкой в разы дольше мака; её берёт регрессия в CI.
Раскладка жадная: наборы по убыванию веса, каждый — в корзину с наименьшей суммой. Шапка называет
выравнивание (`корзин N по времени` или `по размеру`), а по таблице — ещё строкой
`== корзины по времени из <таблица>: вне таблицы наборов M, их вес — медиана X с`. Наборы общих
хабов (тег `хаб:<группа>`) в обычные корзины не идут: их гоняет корзина «хабы»
одновременно с остальными, в своём воркспейсе на том же снимке — поднимает хабы групп инструментом
`tests/инструменты/хаб-группы.os` из этого воркспейса, одним `oneunit` гоняет наборы групп по фазам
и гасит хабы; если она упала, перед остановкой печатаются хвосты журналов хабов. Её состав —
строками `== корзина хабы: <набор>` и группами с фазами, вывод — строками `корзина хабы │`, после
обычных корзин; в сводке она — своей строкой, и её код входит в код прогона. Прерванный прогон
гасит её группой процессов вместе с хабами, а каталоги хабов она снимает сама.

`--время` — диагностика, а не приёмка: каждый отобранный набор идёт своим `oneunit`, в конце —
наборы по убыванию времени (секунды целые, вместе со стартом процесса и `&ПередВсеми`) и та же сводка.
`--таблица-времени <файл>` (только вместе с `--время`, иначе код 2) по итогу прогона записывает
файл целиком в формате таблицы весов корзин — с общими хабами все наборы обоих вызовов. Упавший
набор нового веса не получает: строка берётся из прежней таблицы по этому пути, а без неё набора в
таблице нет, и при раскладке он весит медиану. Таблицу обновляют прогоном
`scripts/тесты.sh --всё --время --таблица-времени scripts/время-наборов.tsv` на свободной машине.
Такой прогон пишет в дерево, поэтому его итог — «дерево менялось по ходу прогона», так и должно быть;
приёмочный прогон идёт без этого ключа. Таблицу CI снимает ручной запуск `test.yaml` с флагом
`time_table` (Actions → Тестирование → Run workflow): вместо регрессии корзинами он гоняет
`scripts/тесты.sh --всё --время --таблица-времени scripts/время-наборов-ci.tsv` на раннере и
выкладывает файл артефактом `время-наборов-ci`; его скачивают и коммитят в `scripts/`.

Наборы `*_Плавающие_Тесты.os` — карантин: тесты, которые под нагрузкой плавают, а поодиночке
зелёные. Их не берёт ни один режим, кроме `--плавающие`; в CI карантин идёт отдельным шагом
регрессии, который конвейер не роняет. Карантинный набор лежит рядом с исходным и повторяет только
подъём и остановку хаба, а помощники берёт из тех же фикстур, что и исходный.

Вывод обоих скриптов открывает шапка прогона и закрывает итог — по ним видно, на каком коде
шёл прогон:

```text
== прогон.коммит: <полный хэш HEAD>
== прогон.дерево: чисто
== прогон.команда: scripts/тесты.sh основа
== прогон.каталог: <корень дерева>
== прогон.начало: <время UTC>
…
== прогон.итог: код 0, коммит <тот же хэш>, дерево чистое и не менялось, конец <время UTC>
```

Незакоммиченные и неотслеживаемые пути шапка перечисляет строками `== прогон.дерево:` (первые 20
и счётчик остальных). Если по ходу прогона сменился коммит или содержимое дерева, итог говорит
«дерево менялось по ходу прогона»: такой прогон не свидетельствует ни о каком коммите. Пути,
которые git игнорирует, в сверку не входят: смену `oscript_modules` по ходу прогона итог не
видит. Вне git-дерева шапка пишет, что коммита нет, и прогон идёт дальше. Все строки ищутся
грепом `^== прогон\.`.

Наборы отбираются файлами: `oneunit execute` без `-f` смотрит только в корень `tests/`, а фильтр
тегов не доходит до наборов, изолированных процессом. Уровни прогона размечены тегами: `хаб` —
наборы, поднимающие живой экземпляр, `внешние` — требующие внешней системы, `смоук` —
доказывающие, что хаб работает по назначению, включая полный цикл `opm push` → `opm install`.

Живые наборы, которым не нужен особый старт, делят хаб своей группы. Группы объявлены в фикстуре
`ГруппыХабов`: имя группы для тега, латинский идентификатор, префикс временного каталога, окружение
и сидеры, которые запускаются по порядку. Набор группы помечен тегами `&Тег("хаб:<группа>")` и
`&Тег("фаза:пусто")`, `"фаза:чтение"`, `"фаза:создание"` или `"фаза:удаление"` (без тега фазы —
создание), несёт `&Порядок(0)`, `(1)`, `(2)` или `(3)` той же фазы и в `&ПередВсеми` берёт хаб
вызовом `ОбщийХаб.Экземпляр("<группа>")`. Фаза «пусто» — проверки хаба, на котором ещё не пройден
мастер `/setup`: набор только читает и мастера не проходит. «Чтение» не меняет предметных фактов хаба (пулы, пакеты, версии,
учётки, права, теги, подписки, зеркала, настройки) и его счётчиков (скачивания); вход и выход
допустимы: сессия и строки журнала аудита — не предметные факты, и набор, читающий журнал аудита,
на его пустоту не опирается. Засев группы и учётка мастера группы «мастер» — факты группы, а не
набора: сидер заводит их до наборов, помощник мастера — в `&ПередВсеми` первого набора фаз «чтение»
и дальше, и набор фазы «чтение» от этого чтением быть не перестаёт. Набор фазы «удаление» уничтожает только то, что создал сам, или
называет в шапке засеянные факты, которые уничтожает; внутри фазы наборы идут по имени, и на этот
порядок они не опираются. Настройку всего хаба (основной пул, ключ настроек) набор группы меняет
только с возвратом: называет её в шапке и возвращает в `&ПослеВсех`. Окружение группы описано в
фикстуре `ГруппыХабов`: у групп с окружением выключены планировщик, доставка вебхуков и
подтверждение почты; у «кабинета» админа заводит сидер, у «пакетов» админ задан окружением, внешний
адрес хаба — `https://hub.example.ru`, предел распакованного пакета поднят, а засев — пакет
`spike0c-testpkg` в пуле `public`. Учётку админа и адрес хаба, заданные окружением группы, набор
берёт из её описания (`ГруппыХабов.Окружение("<группа>", "<переменная>")`), а не повторяет их.
Админа «пакетов» заводит безголовый онбординг с требованием сменить пароль: API ему открыт, а экраны
кабинета уводят на смену пароля, поэтому набору, который ходит по экранам, нужна своя учётка с ролью
на своём пуле.

Группа «мастер» — хаб на пустой базе без админа из окружения и без засева: он ждёт мастера `/setup`,
замок ограничителя входа сокращён до 2 с. Учётку первого администратора группа объявляет в описании
(поле `Мастер`, доступ `ГруппыХабов.Мастер("<группа>")` отказывает, если группа её не объявляет), а не
в окружении: админ из окружения у неё обязан оставаться пустым. Набор фазы «пусто» мастера не проходит;
каждый набор группы фаз «чтение» и дальше в `&ПередВсеми` проходит мастер помощником
`ОбщийХаб.ПройтиМастер(Хаб, "<группа>")` — 201 заводит администратора, 409 значит, что его уже завёл
сосед, — и входит учёткой мастера через `ВойтиДождавшись`, переждав замок, оставленный соседом. Пакетов
и общих пулов наборы группы не заводят: основной пул хаба не назначен, лендинг пуст. Журнал хаба со
строк старта отдаёт `ЭкземплярХаба.ЖурналЦеликом()`: у общего хаба `Дамп()` — хвост журнала с момента
подключения.

В режимах `--e2e`, `<модуль> --e2e` и `--всё` в один поток `scripts/тесты.sh` гоняет два вызова
`oneunit`. Первый — наборы без тега группы, каждый живой набор со своим хабом. Затем скрипт
поднимает по хабу на каждую группу инструментом `tests/инструменты/хаб-группы.os` (строки
`== хаб.<группа>: порт N, pid M`), второй `oneunit` гоняет наборы групп, и хабы гасятся
(`== хаб.<группа>: остановлен, pid M`); если второй вызов упал, перед остановкой печатаются
последние 30 строк журнала каждого хаба с префиксом `хаб.<группа> │`. Фазы во втором вызове держит
`&Порядок`: `oneunit` идёт по `&Порядок` набора, затем по имени, порядок файлов в командной строке
не соблюдает, — сперва фаза «пусто» всех групп, затем чтения, создания и удаления. Сводка строк статистики и
код выхода — по обоим вызовам. С `--параллельно` второй вызов вместе с хабами идёт корзиной «хабы»
рядом с остальными корзинами. Адрес хаба наборы получают переменной
`OSHUB_TEST_HUB_<ИДЕНТИФИКАТОР>=http://127.0.0.1:<порт>`, файл его журнала — переменной
`OSHUB_TEST_HUB_<ИДЕНТИФИКАТОР>_LOG`; такой экземпляр не гасится `Остановить()`, а методы окружения,
базы, сидера и запуска у него отказывают исключением; журнал такой экземпляр читает с момента
подключения. Набор, запущенный поодиночке (`oneunit execute -f`), без переменной поднимает свой хаб
по описанию группы. `--список` печатает оба вызова и группы со счётом наборов по фазам:
`== хаб.<группа>: общий хаб, наборов N, фазы: пусто P → чтение A → создание B → удаление C`. Поднять хаб
группы руками: `oscript tests/инструменты/хаб-группы.os поднять <группа>` печатает переменную, порт,
PID, каталог и журнал; `… остановить <pid> <каталог>` гасит его, если PID принадлежит хабу этого
репозитория, и убирает каталог. Набор к такому хабу подключают экспортом
`OSHUB_TEST_HUB_<ИДЕНТИФИКАТОР>` перед `oneunit execute -f`; `scripts/тесты.sh` в режимах с живыми
наборами переменные `OSHUB_TEST_HUB_*` снимает (строка `== прогон.среда`) и поднимает хабы сам.

Набор подключает библиотеку фикстур относительным путём — `#Использовать "../фикстуры"`, из
`tests/e2e/<модуль>/` — `"../../фикстуры"`, — а фикстуру берёт по имени:
`РеестрФикстур.Подключить("Имя")` находит её и в общем каталоге, и в каталоге фикстур модуля.
Корень репозитория, `src/модули` и `tests` отдаёт `КаталогиПроекта`. Имя файла набора и фикстуры
уникально во всём дереве: оно же имя типа, а тип один на процесс.

Свой хаб набор поднимает фикстурой `ЭкземплярХаба`: порт выдаёт ОС через `ВыдачаПортов`, `Запустить()`
ждёт строки конца старта и `/health` и при перехвате порта повторяет старт на другом. Несколько хабов
набор стартует в `&ПередВсеми` разом: `ЗапуститьВФоне()` у каждого (журнал хаба — в файле), затем
`Дождаться()` у каждого перед первым обращением — с тем же повтором при перехвате порта. Так можно,
потому что окружение у каждого экземпляра своё: `Среда()` задаёт переменную хабу и сидерам экземпляра
(`ЗапуститьСидер`), а переменные хаба (`OSHUB_*`, `OTEL_*`), заданные соседу, у них пусты; окружение
прогона, снятое до фикстур (`ОкружениеПрогона`), сохраняется. Процессу набора `Среда()` ставит переменную
тоже — до `Остановить()`. Поэтому сидер своего хаба набор запускает `ЗапуститьСидер` экземпляра, а не
`СоздатьПроцесс` в самом наборе: такой процесс берёт окружение процесса набора, где лежат переменные
экземпляра, чья `Среда()` вызвана последней. Событие с задержкой (истечение срока, укладка в базу) набор ждёт
опросом с крайним сроком, а не сном на весь срок. Самотесты фикстуры поднимают вместо хаба заглушку
`tests/фикстуры/заглушка-хаба` (`Новый ЭкземплярХаба(<таймаут>, <каталог заглушки>)`): она слушает
`OSHUB_PORT`, отвечает 200 на любой запрос и пишет строку конца старта.

Контейнер ОСени набор собирает из совета `СоветНабора`: `СДетальками(Детальки)` — окружение,
`autumn-properties.json` проекта и детальки набора поверх; `БезФайлаНастроек(Детальки)` — без файла
проекта, когда его узлы (база, корень данных) набору чужие.

## Демо-стенд

```bash
oscript tools/demo.os                 # поднять наполненный хаб на localhost:3380
oscript tools/demo.os --port 8080     # другой порт
oscript tools/demo.os --keep          # не пересоздавать данные, просто поднять
oscript tools/demo.os --no-run        # подготовить стенд и выйти
```

Скрипт поднимает пустой хаб и наполняет его **через тот же HTTP API и те же формы**,
что доступны человеку: пулы, десятки пользователей, группы, права, пакеты, провайдеры
входа, подписки на события, апстримы и зеркала, токены, заявки и резерв имени. Сам хаб
стенда ходит наружу только за публичным хабом апстрима: чаты Telegram фиктивные, а Bot API
хаб зовёт через прокси на несуществующий узел, вебхуки и издатель провайдера из конфигурации —
в зоне `.local`, зеркала и второй апстрим смотрят в пулы этого же хаба. Кнопки GitHub и GitLab
на странице входа уводят браузер на их сайты — с фиктивным client_id. Под конец наполнитель
обходит экраны настроек под `root`: каждый обязан ответить 200, а экран с данными — показать
данные стенда. Адреса стенда знают порт наполнения, поэтому `--keep` на другом порту
наполняет стенд заново. Данные и памятка с учётками — в `./demo` (каталог под `.gitignore`,
пересоздаётся скриптом сколько угодно раз).
Скриншоты в документации сняты с этого стенда.

## Образ и CI

Сборка и запуск контейнера — [docker/README.md](../docker/README.md). Версия живёт
только в `packagedef`: ею помечаются `.ospx`, теги образа и метки OCI.

Пакет `.ospx` собирает `opm build .` после `opm install -l`. Зависимости в него кладёт хук
`ПриСборке` в `packagedef`: рантайм-закрытие `.ЗависитОт` из `./oscript_modules` без
dev-зависимостей, посторонних библиотек, тестов и документации библиотек и компонент, которых
хаб не грузит (отбор — [`tools/ПоставкаЗависимостей.os`](../tools/ПоставкаЗависимостей.os)).
Каталог `oscript_modules` сборка только читает. Если в нём нет библиотеки закрытия, сборка
останавливается и называет её.

| Конвейер | Когда | Что делает |
| --- | --- | --- |
| [`test.yaml`](../.github/workflows/test.yaml) | push в `main`, pull request, ручной запуск | смоук; кроме pull request — регрессия корзинами (`--параллельно` на одну меньше числа ядер раннера, веса `scripts/время-наборов-ci.tsv`) без внешних наборов и наборы на PostgreSQL; ручной запуск с `time_table` вместо корзин снимает таблицу весов CI артефактом |
| [`image.yaml`](../.github/workflows/image.yaml) | push в `main`, pull request, релиз, ручной запуск | сборка образа; на релизе и по ручному запуску с `push` — публикация в Docker Hub. Зависимости конвейеры ставят `opm install -l` из пулов [`opm.cfg`](../opm.cfg) |
| [`release.yaml`](../.github/workflows/release.yaml) | публикация релиза GitHub | сборка `.ospx` и публикация пакета в пул `default` на hub.oscript.io доверенным конвейером |

Хаб выпускается GitHub-релизом с тегом `vX.Y.Z`, где `X.Y.Z` — `.Версия` в `packagedef`:
`release.yaml` публикует `openhub-X.Y.Z.ospx` в пул `default` на hub.oscript.io
[доверенной публикацией](доверенная-публикация.md) — по id-token GitHub Actions, без секретов.
Тег с другим номером конвейер отвергает.
