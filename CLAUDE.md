# OpenHub — правила для AI-сессий

Открытый хаб пакетов OneScript. Стек: чистый OneScript + ОСень (autumn) + winow.

Здесь только правила. История — в `git log`, текущее состояние — в STATUS.md, невосстановимое
из кода — в ЗНАНИЕ.md. Дат, замеров и хроники сюда не пишут.

## Точка входа сессии

⛔ **Рабочая кухня — вне git.** `docs/требования/`, `docs/процесс/`, `issues/`, `spikes/`,
`АНАЛИЗ-*.md`, `scripts/обзор-требований.sh`, `docker/нагрузка/` закрыты `.gitignore`: в клоне
их нет, ссылки ниже живы только у того, кто ведёт проект. Правки в них не версионируются —
копия одна, беречь её.

Начинай с [STATUS.md](docs/процесс/STATUS.md) и каталога требований
[docs/требования/](docs/требования/README.md): история на файл, у каждой — критерии приёмки
и строка «Реализация» (адреса, классы, наборы); очередь «обещано, но не сделано» —
[ОБЗОР.md](docs/требования/ОБЗОР.md). Невосстановимое из кода — [ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md);
выкатка — [ДЕПЛОЙ.md](docs/процесс/ДЕПЛОЙ.md); ручные правки чужих библиотек, которые смывает
`opm install -l`, — [ПАТЧИ-БИБЛИОТЕК.md](docs/процесс/ПАТЧИ-БИБЛИОТЕК.md); раскладка
`src/модули`, контракты и объявления — [РАСКЛАДКА.md](docs/процесс/РАСКЛАДКА.md).

## Оркестрация

### Управляющий агент

- Код не пишет: режет очередь ОБЗОР.md на задачи, ставит их субагентам, проверяет, вливает,
  ведёт STATUS.md. Объёмное чтение, разработку и отладку отдаёт субагентам, себе берёт отчёты.
- Решает сам (приоритеты, обход блокеров), если решение следует из каталога и здравого
  смысла; спорное — в STATUS.md с обоснованием.
- Требования меняет только владелец; следствия отменённой им позиции меняются вместе с ней.
  Названный владельцем способ («средствами X») своим не подменяют: заблокирован — короткий
  вопрос первой строкой, альтернатива — только предложением.
- ⛔ В `main` — только сквош, сообщение по-русски о сути, без trailers (`Co-Authored-By`,
  подписи модели) ни в каких коммитах. В библиотеках (кит — библиотека компонентов
  `oscript-ui`, сателлиты, ветки PR в чужие) правка ложится одним коммитом. Запушенную историю без владельца не переписывают.

### Субагенты

- Все — на Opus (`model: "opus"`): авторы, ревьюеры, вспомогательные; работающих ради
  смены модели не перезапускают.
- Постановка трека (задачи субагента) самодостаточна: пути, требования, критерии готовности,
  состав отчёта. Волна — партия треков, которые вливаются вместе.
- Правящий репозиторий субагент работает в своём git worktree (`isolation: worktree`), даже
  один; интегрирует управляющий. Сателлиты — отдельные репозитории, изоляция не нужна.
- Задача закрыта — воркспейс и ветку снимают после трёх проверок: **влита** (дерево
  `git merge-tree --write-tree main <ветка>` равно дереву `main`), **чиста**
  (`git status --short --untracked-files=all`), **никто не работает** (`lsof -a -p <pid> -d cwd`
  по живым `oscript`/`oneunit`). Не сошлось — не трогать, спросить владельца: снос роняет
  cwd живых процессов в основной чекаут, неотслеживаемое `git` не вернёт.

### Ревью-агенты

- Ревьюер — не автор. Отчёт — замечания с severity; блокирующее = гейт не пройден.
- ⛔ **Тестов ревьюер не гоняет** — сверяет логи автора (гейт 1 ниже); лога нет, хэш не тот,
  уровень не тот, итог не «код 0 … не менялось» — трек возвращается автору, а не перегоняется за него.
- Проверяет гейты; ООП (инкапсуляция, одна ответственность, зависимости через DI ОСени,
  а не `Новый`, без god-objects и дублирования); нейминг; полноту тестов (негатив, границы);
  раскладку по чек-листу раздела «Модули».
- ⛔ **Когнитивный разбор** — диф читают как видящий код впервые и отвечают словами:
  - по смыслу: имя называет, чем вещь является здесь (`Шапка`, а не сквозной `Холст`;
    `ИмяПровайдера`, а не `Надпись2`); композиция — существительное, глагол (`ДобавитьX`)
    выдаёт описание механики;
  - по стилю: один файл — один способ говорить, соседние функции не спорят порядком слов,
    уровнем абстракции и длиной;
  - по форматированию: пустая строка делит смысловые куски, вложенность видна, однотипная
    простыня сгруппирована;
  - сверху вниз: по верхней функции видно, из чего собран экран; слова кита — в
    однострочных сборщиках.

  «Непонятно» — блокирующее; «зато короче» его не снимает.
- ⛔ **Документы приведены в соответствие до слияния** (кухня вне git — чтением файлов):
  сделанное видно в требовании (`Полнота`, «Реализация» с набором-сторожем); снятый механизм
  унёс требование, ключи и ссылки — висячих `ИСТ-*`/`НФТ-*` нет; отработавший документ
  (отвеченный вопрос `спорное/`, разобранные комментарии) удалён; `ОБЗОР.md` пересобран
  `scripts/обзор-требований.sh`, руками не правится. Требование как до работы — гейт не пройден.

### Кволити-гейты

Каждый результат (требование, библиотека, PR) проходит все; не прошедший возвращается автору.
⛔ **Каждую проверку делают один раз, один исполнитель:** повторный прогон того же уровня на том же
коде — двойная работа, а не надёжность.

1. Зелёные тесты OneUnit по уровню задачи и сборка — **гоняет автор**: модуль и смоук, при
   смене интерфейса — потребители. Каждый прогон — скриптом (`scripts/тесты.sh`, `scripts/смоук.sh`)
   в свой лог: вывод открывает шапка `== прогон.*`, закрывает итог `== прогон.итог`. Ревьюер сверяет
   по логу: `прогон.коммит` = ревьюируемый коммит, `прогон.дерево: чисто`, `прогон.команда` нужного
   уровня, ноль ошибочных, строка «Тестирование завершилось удачно», последней — итог
   `код 0, коммит <тот же>, дерево чистое и не менялось`; «дерево менялось по ходу прогона» — прогона нет.
   Круг правок — автор перегоняет только затронутые модули, ревьюер смотрит диф круга и новый лог.
   Как треки работают вместе, проверяет только регрессия волны (раздел «Тесты»).
2. Соответствие требованию: каждый критерий приёмки наблюдаем и стережётся набором,
   «Полнота» и «Реализация» пересняты по факту. Работа не закрывает ничьей истории —
   спроси владельца, а не дописывай историю под готовый код.
3. У библиотеки полный состав: packagedef, tests, README, LICENSE.
4. Ревью отдельным агентом пройдено, замечания исправлены.
5. ⛔ Мутационная проверка сторожей поведения — **один раз в конце, после всех приёмок,
   по запросу владельца**; в треках и на ревью мутаций нет. Ломают продукт — набор обязан
   покраснеть; мутируют только закоммиченное, откатывают до любого `git add`, итог — в отчёте.

Сторожа (тесты, держащие инвариант):

- Стерегут инвариант, а не форму записи: текстовую сверку обходят регистром, скобками,
  селектором. Выразим на значении — стереги значение; текстовый скан — вторая сеть.
- Сканер исходников (`.os`, `.css`, манифесты, YAML) снимает и комментарии, и строковые
  литералы; у каждого — самотест «литерал — не директива».
- ⛔ Тест — на то, что ломается у пользователя: страница, форма, иконка, ответ адреса.
  Состав дерева (лишний файл, класс не в том модуле, слово в литерале, разметка не там)
  автоматикой не проверяют — это ревью по дифу. Исключение — уникальность базовых имён
  классов: её нарушение роняет старт.
- ⛔ Размер файла не проверяется ничем: читаемость дороже строк, класс режут по
  ответственности, а не по числу строк.

### STATUS.md и ЗНАНИЕ.md

- STATUS.md (`docs/процесс/`) — по-русски, текстом и таблицами, не логом; управляющий
  обновляет его после каждого значимого события, новая сессия продолжает по нему. Разделы:
  что закрывается; что сделано (с датами); что в работе (субагенты, требования, воркспейсы);
  что дальше; журнал решений с обоснованиями; блокеры и риски. Только живое: закрытая
  хроника и кикоффы прошлых волн уходят.
- ЗНАНИЕ.md — только невосстановимое из кода: питфол, дефект чужой библиотеки, риск, замер.
  Устаревшее правят или удаляют. Правит управляющий.

## Модули

`src/модули` — шесть слоёв. Граница модуля — соглашение (имена классов глобальны), держит
её ревью.

| Слой | Модули |
| --- | --- |
| L0 платформа, о хабе не знает | `основа`, `сеть`, `данные`, `наблюдаемость`, `фоновыеЗадания` |
| L1 службы инсталляции | `события`, `аудит`, `настройки`, `происшествия`, `хранилище`, `почта`, `гео`, `уведомления`, `статистика`, `описания`, `протоколAPI` |
| L2 предметы | `реестр`, `права`, `вход`, `прокси`, `зеркала`, `публикация`, `подписки`, `поиск` |
| L3 сценарии | `кабинет`, `состояние` |
| L4 ворота | `api`, `интерфейс` |
| L5 запуск | `запуск` |

- **Ребро только вниз** (вбок в слое — без цикла). `основа` не знает хаба, `данные` —
  техника доступа к базе без таблиц.
- **Нижнему нужно знание верхнего — контракт-желудь:** класс без `&Желудь` у нижнего;
  реализация у верхнего — `&Желудь` + `&Прозвище("<Контракт>")` (+ `&Порядок(N)`);
  потребитель — `&Пластилин(Значение = "<Контракт>")` или `…, Тип = "Массив")`; если без
  реализации он теряет смысл, на `Неопределено` или пустом массиве отказывает громко.
  Нижний сам умеет нужное — верхний зовёт его напрямую.
- **Таблица у предмета:** `&Сущность` и `Хранилище*` — в модуле-хозяине. Чужое
  `Хранилище*` — не дверь, соседи зовут службу модуля.
- **Реестры-перечни — из объявлений** модулей-владельцев: `КлючиНастроек<Предмет>`,
  `КодыПроисшествий<Подсистема>`, `ОписанияСобытий<Предмет>`, `Задача<Что>`; шаблон имени
  обязателен — фикстуры ищут объявления по префиксу.
- **Публичный интерфейс** — то, что зовут соседи: желуди по имени или прозвищу, контракты,
  службы и их сигнатуры. Остальное — внутренность модуля.
- **README модуля** — по шаблону: назначение; публичный интерфейс; зависимости; настройки;
  где что лежит; инварианты; тесты.
- **Проверка изменения:** внутри модуля — `scripts/тесты.sh <модуль>` и смоук; сменился
  интерфейс (метод, сигнатура, желудь, прозвище, параметр конструктора) — плюс
  `--с-потребителями`.
- **Имя класса уникально во всём дереве:** одинаковые базовые имена роняют старт; контракт
  занимает имя, реализация называется по-своему.

Раскладку проверяют глазами по дифу (полностью — РАСКЛАДКА.md). Чаще всего нарушают:

- каталог называет предмет, а не вид класса; подкаталог — по сюжету; в корне `Классы/`
  разрезанного модуля файлов нет, общее — в `общее/`;
- разметку печатают только кит и `интерфейс`; в домене, службах и обработчиках
  вебхуков тегов нет; кит не знает хаба — ни доменных классов, ни слов `пакет`, `пул`,
  `версия`, `тег` в литералах;
- в `интерфейс` — только видимое пользователю: потребляемое `api` или доменом там не живёт;
  `интерфейс/Классы/<раздел>` называется экраном;
- у экрана настроек один хозяин (пул, пакет, группа, хаб, аккаунт) — контроллер двух
  хозяев показывает чужое;
- новый модуль получает `tests/<модуль>/` и попадает в обвязки, перечисляющие модули руками.

## ⛔ Правила слоя данных — нарушение отменяет работу

**1. База — только через autumn-data.** Коннекторы не подменяют и не оборачивают,
`oscript_modules` не трогают, сырого entity нет. Одна таблица — один `Хранилище*`
с `&ХранилищеСущностей`: заглушки `&МетодЗапроса` и доменные методы рядом. Выборки строк
и страницы — только деривацией; доменный метод зовёт её через Табакерку с собой:
`&Табакерка &Пластилин(Значение = "<своё имя>") _Сам` в конструкторе,
`Сам.Достать().ПолучитьПо…(…)` в теле (прямой самовызов вернёт `Неопределено`, ЗНАНИЕ §5.2).
`&Родитель`, `МенеджерСущностей`, `ХранилищеСущностей.Получить(ОпцииПоиска)`, ручные
`ОпцииПоиска` для выборки — нет; выборка, которую имя метода не выражает, — вопрос владельцу.
**SQL — только агрегаты** (COUNT, SUM, EXISTS, группировка) через `ВычислитьСКоннектором`
одной дверью `АгрегатыБазы` (НФТ-ЭКСП-015): текст — из имён `ОбъектМодели`, значения —
одной дверью, фильтр — `ОпцииПоиска`, у каждого агрегата фолбэк на выборку для бэкендов
без SQL (`КоннекторJSON`, `КоннекторInMemory`). `SELECT *`, `UPDATE`, `DELETE` руками — нет.
Дефект entity или autumn-data — issue в апстрим, а не обход у себя.

**2. Дефект доказывают воспроизведением в реальной работе** с описанием «как это увидит
пользователь хаба». Синтетический тест библиотеки в отрыве от продукта — не доказательство
и в дерево не берётся.

**3. Миграций нет.** Схему строит авто-DDL entity; изменение модели — правка сущностей.
Долг данных одной инсталляции чинят разово (admin-cli, скрипт), не механизмом в продукте.
Индексы не заводят: приложение не знает, какой под ним бэкенд.

**4. Уникальность держит приложение, а не база:** проверка в сервисном слое на любом бэкенде
и негативный тест на дубль. Объявляет уникальность её требование, называя набор-сторож
в «Реализации» (`ИСТ-ДОСТ-029` — почта учётки, `ИСТ-ПУЛ-002` — имя пакета в пуле,
`ИСТ-ПУЛ-003` — имя пула).

## Общие правила

- Нейминг — родной осенний (`&Желудь`, `&Пластилин`, `&Рогатка`, `&Напильник`), не killjoy-flavour.
- Markdown — библиотека oscript-md (автор — владелец), свою не писать.
- Среда — OneScript с сайта как есть. В рантайме (`src/`, образ, `docker/`, скрипты
  запуска) Python нет без согласования; в тестах и командах агента — можно.
- Дефект чужой библиотеки не обходят: issue автору с воспроизведением, следствие — пропуском
  в `tests/сквозные/ДефектыБиблиотек_Тесты.os`; обёрток «пока не починят» нет.
- **Публичные тексты** (README корня и модулей, `docs/*.md`, `docker/README.md`, шапки
  скриптов и workflow, `packagedef`) — только текущее состояние: куда смотреть, что делать.
  Без хроники, «было — стало», дат, решений владельца, чисел тестов, рассказов о дефектах
  и ссылок на кухню (этот файл — исключение). Поведение изменилось — текст тем же коммитом.
- **Код — лучший комментарий.** Шапка модуля — 1–2 строки о содержимом. Экспортные методы —
  по стандарту 1С (назначение, `Параметры:`, `Возвращаемое значение:`), только контракт: без
  ссылок на документацию, требований и истории. `ПриСозданииОбъекта` не документируют.
  Неэкспортному — максимум строка о неочевидном. Дефекты, риски, питфолы — в ЗНАНИЕ.md;
  требование называет код в «Реализации», код о требовании не знает.

### Тесты

- OneUnit (+asserts). Готово = код + тесты + зелёный CI. MCP из `.mcp.json` (`run_tests`,
  `discover_tests`) подкаталогов не видит — каталог модуля передают явно.
- Раскладка (подробно — `docs/разработка.md`): `tests/<модуль>/` и его `фикстуры/`;
  `tests/e2e/<модуль>/` — живой хаб; `tests/сквозные/` — линты дерева и глобальные
  инварианты; `tests/инфраструктура/` — самотесты обвязки; `tests/внешние/` — MinIO,
  PostgreSQL, живой hub.oscript.io; `tests/фикстуры/` — общие фикстуры.

| Уровень | Команда | Когда |
| --- | --- | --- |
| смоук | `scripts/смоук.sh` | после каждого шага; автор — в конце круга |
| модуль | `scripts/тесты.sh <модуль>` (свои и `сквозные/`), `--e2e` — плюс живые модуля | перед коммитом правки модуля |
| потребители | `scripts/тесты.sh <модуль> --с-потребителями` | сменился интерфейс модуля |
| инфраструктура | `scripts/тесты.sh --инфраструктура` | правка `scripts/` или `tests/инфраструктура/` |
| регрессия | `scripts/тесты.sh --всё` | один раз на волну, на замороженном `main` |
| внешние | `scripts/тесты.sh --внешние` + `OSHUB_S3_SMOKE`, `OSHUB_TEST_PG_DSN`, `OSHUB_MIRROR_LIVE` | руками, при поднятых MinIO и PostgreSQL |

`scripts/тесты.sh --e2e` — все живые наборы; `<модуль> --список` — что попадёт в прогон.

- Наборы отбирают скрипты файлами: голый `oneunit execute` видит только корень `tests/`,
  фильтр тегов не доходит до наборов с `&Изолированный(Уровень = "Процесс")` — поэтому
  `-T хаб` почти ничего не экономит (разметку при этом не снимают).
- Теги: `хаб` обязателен набору, поднимающему живой хаб (`ЭкземплярХаба`), — такие наборы
  модуля лежат в `tests/e2e/<модуль>/`; `внешние` — нужна внешняя система, `tests/внешние/`;
  можно оба. `смоук` — на существующих методах, доказывающих назначение хаба, включая
  `opm push` → `opm install`; смоук пополняют тегом, своих тестов не заводят.
- ⚠ Тег вешается на набор целиком, `-T` исключает весь набор: живому тесту — отдельный
  набор, offline-проверки — без тега. Сторож, который не запускается, — не сторож.
- ⛔ **Регрессия одна на волну** — в конце, на `main` после сквоша всех треков (при выпуске —
  параллельно со сборкой образа), гоняет управляющий. Автор гоняет свои наборы, потребителей
  при смене интерфейса и смоук; ревьюер не гоняет ничего; трек после регрессии принимают так же.
  Перебазированную на свежий `main` ветку перед сквошем не перегоняют — совместную работу
  треков ловит регрессия. Второй полный прогон — только по слову владельца.
- ⛔ **Регрессию гоняют в неизменном дереве** — отдельный воркспейс на замороженном коммите
  со своим `oscript_modules`: наборы читают файлы по ходу прогона, правка или второй прогон
  в том же чекауте дают ложный красный.
- Приёмка прогона (ЗНАНИЕ §6.2): ноль ошибочных наборов и тестов, тестов обнаружено
  не меньше эталона, строка «Тестирование завершилось удачно» и последней — итог
  `== прогон.итог: код 0, …, дерево чистое и не менялось`. Эталон регрессии — в STATUS.md.
- Регрессия не ходит к чужим серверам: живой тест — в `tests/внешние/`, проверяемое им
  правило — одной копией в фикстуре (`ДоступностьАпстрима`), её сторож —
  `tests/инфраструктура/ДоступностьАпстрима_Тесты.os` в регрессии.
- Плавают под нагрузкой, поодиночке зелёные: `АдминAPIHTTP_Тесты` —
  `ЗеркалаПулаЖивутПолнымЦикломУАдминистратораПула`, `ТокенЗеркалаЗадаётсяAPIНоОбратноНеВыдаётся`,
  `ЗаданиеДоставкиЛожитсяВБазуИРазбираетсяФоном`, `МусорВПолеMigrateДаётОбычноеЗеркалоИЧестныйОтвет` (гонка
  read-modify-write в домене зеркал, ЗНАНИЕ §3.6; заведение зеркала отвечает 422 вместо 201).
  Увидел их — перепроверь набор точечно; новое имя — находка.
- Ключи настроек модуля в юнит-контейнере едут за его классами (`КлассыСлоя.Подключить*` →
  `РеестрНастроекХаба.ПодключитьКлассы`); набору, чьё поведение зависит от чужого объявления ключа, —
  `РеестрНастроекХаба.ПодключитьКлючиМодулей("<модуль>")`; полный сбор всех объявлений — только
  сторожу полноты реестра.
- Фикстуры — через реестр: `#Использовать "../фикстуры"` (из `tests/e2e/<модуль>/` —
  `"../../фикстуры"`) рядом с `#Использовать asserts`, дальше `РеестрФикстур.Подключить("Имя")`
  строкой на фикстуру. Продуктовые классы — `КлассыСлоя`, корни — `КаталогиПроекта`. Голого
  `ПодключитьСценарий` в наборе общего процесса нет: имена типов глобальны, повторное
  подключение изменённого файла роняет набор (ЗНАНИЕ §2.1); допустимо в `&ПередВсеми`
  изолированного набора. Имя файла набора и фикстуры уникально в дереве. Набор контракта
  подключает реализации (`КлассыСлоя.ПодключитьРеализации`), иначе массив пуст.
- Один набор не заменяет прогона модуля: линты `tests/сквозные/` (`ЖурналРасследования_Тесты` —
  шаблон журнала литералом, арность через `СтрШаблон`; `КаталогСобытий_Тесты` — `СервисВерсий`)
  входят в `scripts/тесты.sh <модуль>`: `СловарьТекстов_Тесты` — русские литералы и ключи словаря
  в модулях с текстами экранов и в ките (слова журнала — литералом первым аргументом `Лог.*`; домен
  входа читает свой `СловарьВхода`). Сверх того: сменился контракт службы с фейками в `фикстуры/` —
  набор каждого фейка (грепом по имени класса).
