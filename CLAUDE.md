# OpenHub — правила для AI-сессий

Открытый хаб пакетов OneScript. Стек: чистый OneScript + ОСень (autumn) + winow.

**Точка входа новой сессии — [docs/процесс/STATUS.md](docs/процесс/STATUS.md) плюс каталог
требований [docs/требования/](docs/требования/README.md).** Что хаб делает и каким должен
быть — только каталог: одна история на файл, у каждой — критерии приёмки и строка
«Реализация» с адресами, классами и наборами, которые её держат. Проектных глав `docs/NN-*`
больше нет, они снесены 2026-08-07 как отработавшая форма.
Накопленное знание (дефекты чужих библиотек, питфолы платформы, принятые риски) —
[docs/процесс/ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md). Как новая версия доезжает до боевой
инсталляции (образ, манифесты, ArgoCD) — [docs/процесс/ДЕПЛОЙ.md](docs/процесс/ДЕПЛОЙ.md).
Правки, наложенные руками на чужие библиотеки в `oscript_modules` (их смывает
`opm install -l`) — [docs/процесс/ПАТЧИ-БИБЛИОТЕК.md](docs/процесс/ПАТЧИ-БИБЛИОТЕК.md).
Где что лежит в `src/модули` и почему именно так — [docs/процесс/РАСКЛАДКА.md](docs/процесс/РАСКЛАДКА.md).

⛔ **Всё перечисленное живёт только на машине разработчика: с 2026-08-11 эти документы
не в индексе git.** Решение владельца при подготовке релиза: в поставку хаба идут
пользовательские README и статьи `docs/*.md`, а рабочая кухня — нет. Под `.gitignore`
ушли `docs/требования/`, `docs/процесс/`, `issues/`, `spikes/` и `АНАЛИЗ-*.md`; их история
до этого дня лежит в git и поднимается оттуда. Следствия, которые надо помнить:

- **свежий клон этих файлов не содержит.** Ссылки выше рабочие у того, кто ведёт проект,
  и битые у того, кто только что склонировал репозиторий;
- **правки STATUS.md и требований больше не версионируются** — их не спасёт ни коммит,
  ни откат. Терять их нельзя: копия только одна, на диске;
- **ревью «документы приведены в соответствие» это не отменяет.** Требование по-прежнему
  пересниматься обязано (см. ниже); просто изменение не будет видно в дифе, и проверяется
  оно чтением самого файла.

## Оркестрация разработки

Разработка ведётся мультиагентно. Роли жёстко разделены:

### 1. Управляющий агент (менеджер-сессия)

- **Сам код не пишет.** Его работа: декомпозиция очереди «обещано, но не сделано»
  из [docs/требования/ОБЗОР.md](docs/требования/ОБЗОР.md) — она собирается из поля
  «Полнота» и заменяет прежний пошаговый план; постановка задач субагентам, валидация
  результатов, мерж, ведение статуса.
- **Бережно относится к контексту:** объёмную работу (чтение больших исходников,
  разработка, отладка) делегирует субагентам, в свой контекст принимает только их
  отчёты и выводы.
- **Отвечает за проект от начала до конца**: самостоятельно принимает решения о
  приоритетах, воркэраундах, обходах блокеров — не останавливается в ожидании указаний,
  если решение можно принять на основе каталога требований и здравого смысла. Спорные
  решения фиксирует в STATUS.md с обоснованием.
- **Поддерживает STATUS.md актуальным** (см. ниже) — на случай разрыва связи работа
  должна возобновляться новой сессией только по STATUS.md + каталогу требований.

### 2. Субагенты-разработчики

- **Все субагенты запускаются на Opus 5** (в Agent-туле — `model: "opus"`); полные
  правила запуска агентов — [AGENTS.md](AGENTS.md).
- Всю разработку выполняют субагенты; постановка задачи — самодостаточная: пути,
  идентификаторы требований каталога, критерии готовности, что вернуть в отчёте.
- **Два и более субагентов над одним репозиторием параллельно — только в изолированных
  воркспейсах** (git worktree; для Agent-тула — `isolation: worktree`). Интеграцию
  результатов выполняет управляющий агент.
- **Задача закрыта — воркспейс и ветка снимаются.** Влил результат в `main` — сразу
  `git worktree remove` и `git branch -d`; чужого мусора после себя не оставляем.
  За волну 2026-08-10 так накопилось **53 воркспейса и 53 ветки**, из которых 49 были
  пустыми: ни одного коммита сверх `main`. Перед снятием — три проверки, каждая спасает
  чужую работу: **ветка влита** (`git log main..<ветка>` пуст), **воркспейс чист**
  (`git status --short`, включая неотслеживаемые файлы), **внутри никто не работает**
  (`lsof -a -p <pid> -d cwd` для живых `oscript`/`oneunit`). Не сошлось хоть одно —
  воркспейс не трогаем и спрашиваем владельца: снос уронит cwd работающих процессов
  в основной чекаут, а неотслеживаемые файлы не вернёт никакой `git`.
- Библиотеки-сателлиты — отдельные репозитории (см. ниже), их можно вести параллельно
  без изоляции.

### 3. Кволити-гейты

Каждый результат (требование, библиотека, PR) проходит гейты — без исключений:

1. зелёные тесты OneUnit (юнит/интеграционные по уровню задачи) + сборка;
2. **соответствие требованию из каталога и его критериям приёмки**: работа закрыта, когда
   каждый критерий приёмки наблюдаем и стережётся набором, а поля «Полнота» и «Реализация»
   в самом требовании пересняты по факту. Требование заводит владелец: если работа ничьей
   истории не закрывает — это повод спросить, а не дописать историю под уже готовый код;
3. для библиотек — полный обязательный состав (packagedef, tests, README, LICENSE);
4. ревью отдельным агентом (см. ниже) — пройдено, замечания исправлены;
5. **каждый новый сторож доказан мутацией** — ломаем продукт, набор обязан покраснеть,
   мутация откатывается, результат приводится в отчёте.

**Сканер исходников читает код, а не текст.** Разбор `.os`, `.css`, манифестов и YAML идёт
по варианту, снимающему **и комментарии, и строковые литералы**, а на каждый сканер ставится
самотест «литерал — не директива». Волна 2026-08-03 дала три независимых случая, где сканер
читал литерал как код: ложная защита (сторож зелен при сломанном продукте) и ложный отказ
(красный на образце в тесте) — обе стороны одной ошибки.

**⛔ Размер файла не проверяется ничем.** Решение владельца (2026-08-08), дословно:
«**первым делом убери проверку на длину файлов. тут мы боремся за когнитивную понятность,
если это делает файл длиннее — ну что поделать**». Храповик размера снят целиком
(`tests/РазмерКлассов_Тесты.os` удалён), нового не заводить: читаемость дороже строк.
Разрезать класс по-прежнему можно и нужно — но по **ответственности**, потому что
разрезание делает код понятнее, а не потому что число перевалило порог. Требование
порога само порождало непонятность: экран провайдеров лишился блока полей ровно затем,
чтобы влезть в 400 строк.

**Сторож стережёт инвариант, а не форму записи.** Проверка, сверяющая текст, обходится
тривиальной правкой — за одну волну сторожей обходили строчной буквой в ключе, отсутствующими
скобками, заглавной в тексте, селектором по `id`, `!important`, кодом за закрывающей кавычкой
многострочного литерала. Если инвариант выразим на значении — стереги значение; текстовый
скан оставляй второй сетью, а не единственной.

**⛔ Правила раскладки — предмет ревью, а не автотестов.** Решение владельца (2026-08-04).
Тест пишется на то, что **ломается для пользователя**: страница отдаёт не то, форма не
работает, иконка не рисуется, адрес отвечает не так. Всё, что стережёт **состав дерева** —
«появился файл, о котором тесты не знают», «пропал каталог», «класс переехал не туда»,
«в литерале не то слово», «разметка печатается не в том модуле», — автоматикой **не
проверяется**. Такие вещи видит человек и ревью-агент, глядя на диф: «эй, у тебя разметка
не там, где надо». Владелец вычитывает код перед продом глазами, и подстраховка от того,
что он чего-то не заметит, ему не нужна.

Волна 2026-08-04 была потрачена ровно на это: управляющий навесил слой сканеров состава
дерева (разрез модулей, скан литералов кита, храповик состава каталога иконок, политика
содержимого `.svg` с самописным разбором HTML) и три круга ревью гонял по ним автора.
Всё снято. Пятый гейт остаётся, но применяется **к сторожам поведения**: завёл проверку
поведения — докажи мутацией; проверок раскладки не заводи вовсе.

Результат, не прошедший гейт, возвращается на доработку субагенту-автору.

**Почему пятый гейт появился (волна 2026-08-02/03).** Из пяти треков четыре прошли ревью
только со второго захода, и **каждый раз находка приходила из мутации продукта, а не из
чтения кода**: чтение подтверждало, что код выглядит правильным. Краснеть отказывались
тесты, которые выглядели защитой: сторож сравнивал селекторы точным равенством и
обходился составным; сторож проверял порядок строк, но не тип кнопки; сканер мёртвых
правил питался собственными комментариями; тест читал состояние соседей по набору;
граница «истекает ровно сейчас» не покрывалась вовсе. Ни одно из этих мест не было
видно глазами — все найдены тем, что продукт ломали и смотрели, заметит ли набор.

**Мутацию откатывать до любого `git add`.** Однажды `git add -A` прошёл, пока файл был
подменён, и снятая защита уехала в коммит как обычный код при зелёном тесте.

### 4. Ревью-агенты

- Ревью выполняют **отдельные агенты, не авторы кода**.
- Проверяют: соответствие кволити-гейтам; **принципы ООП** — инкапсуляция, единственная
  ответственность классов, зависимости через DI ОСени (интерфейсы-желуди, а не прямое
  создание), отсутствие god-objects и дублирования; нейминг экосистемы; полноту тестов
  (негативные сценарии, граничные случаи).
- Отчёт ревью — список замечаний с severity; блокирующие замечания = непройденный гейт.

**⛔ Обязательный пункт ревьюера: когнитивный разбор.** Решение владельца (2026-08-08).
Ревьюер читает диф **как человек, который видит этот код впервые**, и отвечает словами,
а не галочкой:

- **понятно ли по смыслу.** Имя называет то, чем вещь является в этом месте: `Шапка`,
  а не сквозной `Холст`; `ИмяПровайдера`, а не `Надпись2`. Функция композиции возвращает
  элемент и читается существительным; глаголы (`ДобавитьX`, `НаполнитьY`) — признак того,
  что имя описывает механику, а не содержание;
- **понятно ли стилистически.** Один файл — один способ говорить: соседние функции не
  спорят друг с другом порядком слов, уровнем абстракции и длиной;
- **помогает ли форматирование читать структуру.** Пустая строка отделяет смысловые
  куски, вложенность видна глазом, длинная простыня однотипных строк сгруппирована;
- **виден ли экран сверху вниз.** Читая только верхнюю функцию, человек понимает, из чего
  собран экран; китовые слова спрятаны внутрь однострочных сборщиков.

Замечание «непонятно» — законное и блокирующее. Ответ «зато короче» им не является:
размер файла не ограничен ничем (см. выше).

**⛔ Отдельный пункт ревьюера: документы приведены в соответствие до слияния.** Решение
владельца (2026-08-07), дословно: «**НЕ забывай удалять\редактировать документы перед
слиянием. Поставь отдельный пункт ревьюеру, чтобы проверял. Если что-то сделано
по требованию — в требовании должно быть это отображено**». Проверяется по дифу:

- сделанное по требованию **видно в требовании**: `Полнота` переснята, «Реализация»
  называет адреса, классы и набор, который держит критерий приёмки;
- снятый механизм унёс своё требование, свои ключи и свои ссылки: висячих `ИСТ-*`
  и `НФТ-*` в дереве не осталось;
- отработавший документ удалён, а не оставлен «на память»: отвеченный вопрос из
  `спорное/` исчезает, разобранный файл комментариев — под нож;
- `ОБЗОР.md` пересобран `scripts/обзор-требований.sh` — он производный, руками не правится.

Работа, после которой требование выглядит как до неё, гейт не проходит.

**Чек-лист раскладки — глазами по дифу, кодом не проверяется** (см. запрет выше). Правило
целиком — [docs/процесс/РАСКЛАДКА.md](docs/процесс/РАСКЛАДКА.md), здесь только то, что
чаще всего нарушают:

- разметку печатают только кит (библиотека `oscript-ui`) и модуль интерфейса `web-ui`;
  в доменных модулях, службах и обработчиках вебхуков тегов быть не должно;
- кит не знает о хабе: ни зависимостей на доменные классы, ни слов `пакет`, `пул`,
  `версия`, `тег` в литералах. Знает хаб о ките, не наоборот. С 2026-08-08 это стережёт
  сама граница репозиториев: кит — отдельный сателлит `oscript-ui`, в `src/модули` его нет;
- `web-ui` — только то, что видит пользователь. Класс, которого потребляет `api` или
  доменный модуль, в `web-ui` не живёт: зависимость «не-интерфейс → интерфейс» это
  инверсия слоёв;
- каталог `web-ui/Классы/<раздел>` называется представлением, а не видом класса; в корне
  `Классы/` файлов нет;
- новый модуль в `src/модули` — повод проверить, что он попал в тестовые обвязки, которые
  перечисляют модули руками;
- один экран — один дом настроек: контроллер, обслуживающий два дома сразу, показывает
  чужое (так родился дефект З-10).

### STATUS.md — отчётный документ

- Живёт в `docs/процесс/` вместе с [ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md), **на русском,
  в читаемом виде** (связный текст и таблицы, не служебный лог).
- Обновляется управляющим агентом после каждого значимого события: закрытое или
  провалившееся требование, запуск субагентов, принятое решение, обнаруженный блокер.
- Структура: что закрывается сейчас; что сделано (с датами); что в работе прямо сейчас
  (какие субагенты, над какими требованиями, в каких воркспейсах); что следующее;
  журнал решений с обоснованиями; блокеры и риски.
- **Держится коротким: только живое.** Закрытая хроника (принятые требования, круги
  ревью, снятые блокеры, инциденты) в документе не остаётся — она живёт в истории git,
  иначе документ перестаёт работать как точка входа новой сессии. В
  [ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md) переносится не хроника, а то, что **невосстановимо
  из кода**: питфол платформы, дефект чужой библиотеки, принятый риск, замер. Кикоффы
  прошлых волн удаляются как отработавшие: их содержание либо перенесено в кикофф
  текущей волны, либо поднимается из истории git.

## ⛔ Правила слоя данных — нарушение отменяет работу

**1. Всё взаимодействие с базой — только через autumn-data. Обходов нет.** Сырого SQL в
проекте нет вовсе; коннекторы не подменяются и не оборачиваются; `oscript_modules` не
трогаем. **Документация библиотеки первична:** что она разрешает — разрешено, включая
`ОпцииПоиска` для сложных запросов (docs autumn-data, «Методы запросов», раздел
«Ограничения»). Своих правил строже библиотечных не заводим.
Нашёл дефект entity или autumn-data — **опиши его и заведи issue в апстрим**, а не обходи
у себя: обход прячет проблему и оставляет её всем остальным пользователям библиотеки.

**2. Дефект доказывается воспроизведением в реальной работе, а не синтетическим тестом.**
«Как это увидит пользователь хаба» — обязательная часть описания. Параллельный тест,
воспроизводящий поведение библиотеки в отрыве от продукта, доказательством не является
и в дерево не берётся.

**3. Миграций в проекте нет.** Механизм выпилен целиком по решению владельца: боевых
инсталляций не существует, всё разворачивается с нуля, схему строит авто-DDL entity.
Изменение модели данных = правка сущностей, и только. Индексы не заводим — приложение
не знает и не должно знать, какой бэкенд под ним.

**4. Уникальность критичных сущностей держит приложение, а не база.** Проверка живёт
в сервисном слое и работает на любом бэкенде — в том числе на таком, где никаких
ограничений нет. Заводишь сущность с уникальным ключом — пиши проверку в сервисе и
негативный тест на дубль. Общей таблицы инвариантов больше нет: уникальность объявляет
то требование, которому она принадлежит (`ИСТ-ДОСТ-029` — адрес почты в учётке,
`ИСТ-ПУЛ-002` — имя пакета в пуле, `ИСТ-ПУЛ-003` — имя пула), и там же в строке
«Реализация» назван набор, который её стережёт.

## Общие правила

- Нейминг — родной осенний (&Желудь, &Пластилин, &Рогатка, &Напильник); killjoy-flavour
  не использовать.
- Тесты — OneUnit (+asserts), MCP-сервер подключён через `.mcp.json` (`run_tests` /
  `discover_tests`, тесты в `./tests`). Definition of Done любого шага: код + тесты +
  зелёный CI. Работа без тестов не считается завершённой.
- **Уровни прогона размечены тегами OneUnit.** `&Тег("хаб")` — на 40 наборах (пересчёт 2026-09-04), поднимающих
  живой хаб фикстурой `ЭкземплярХаба`; `&Тег("внешние")` — на четырёх наборах, которым нужна
  внешняя система (`S3СмоукMinIO`, `СмокБэкендов`, `ЗеркалоАпстримЖивой`,
  `ЗеркалоРеальныйАпстрим`); набор вправе нести оба тега сразу — OneUnit собирает все
  аннотации `Тег` конструктора, и живая приёмка зеркала помечена и «хаб», и «внешние»;
  `&Тег("смоук")` — на семи
  существующих методах, доказывающих, что хаб работает по назначению, включая полный цикл
  `opm push` → `opm install`. Новый набор с живым хабом обязан получить `&Тег("хаб")`
  в шапке; смоук пополняется только тегом на существующем тесте, своих тестов не заводит.

  ⚠ **Тег вешается на набор целиком, поэтому один живой тест уносит из прогона весь набор.**
  За волну 2026-08-05 так вышло, что двенадцать offline-тестов, доказывающих починку дефекта
  владельца, не гонялись ни быстрым уровнем, ни регрессией: набор нёс `&Тег("внешние")`
  ради единственного теста против живого `hub.oscript.io`, а `-T` — это **исключение**
  набора. Сторож, который не запускается, — не сторож. Нужен живой тест — заводи ему
  отдельный набор, а offline-проверки оставляй без тега.

  одного байта до границы квоты). Гонку «мутация зеркала под фоновым рабочим» стоит
  починить по существу: снаружи она видна как 500 администратору.

  Числа — эталон приёмки уровня. Регрессия обязана быть зелёной с нулём ошибочных наборов.
  Относительно полного прогона она теряет ровно четыре набора с `&Тег("внешние")` —
  `S3СмоукMinIO` (4 теста), `СмокБэкендов` (5), `ЗеркалоАпстримЖивой` (3),
  `ЗеркалоРеальныйАпстрим` (1), итого **13 тестов**.

  ⚠ **Сеть в регрессии — это чужой сервер в роли гейта.** `РеальныйHubЗеркалируется` ходил
  в живой `hub.oscript.io` из набора БЕЗ тега, и «ноль ошибочных» переставал зависеть от нас:
  во втором прогоне 2026-08-08 хаб с апстримом на публичный хаб не написал «Стартовые задачи
  завершены» за 60 с. Приёмка вынесена набором `ЗеркалоРеальныйАпстрим_Тесты`. Правило её
  предиката (`ОтветОзначаетДоступность`) живёт в фикстуре `ДоступностьАпстрима`: сторож правила
  остался в регрессии, а в сеть ходит только внешний набор — копии правила нет, иначе сторож
  защищал бы не ту копию.

  ⚠ Строка «всё» — замер до прополки зависимостей, переснять не на чем: нужны поднятые
  MinIO и PostgreSQL. Первый, у кого они подняты, обязан обновить число здесь.

  ⚠ **Точечные батареи не заменяют полной регрессии: линты и событийные наборы живут отдельно.**
  Трек, трогающий `src/модули/интерфейс`, обязан гонять `КомпонентыUI_Тесты` (линты слоя
  представления: словарь строк и т.п.); трогающий `СервисВерсий` — `КаталогСобытий_Тесты`.
  Урок трека П (2026-09-02): оба набора не гонял никто, две поломки нашла только полная
  регрессия ревьюера.

  Смоук гоняется скриптом, а не `oneunit execute -t смоук`, потому что прямая команда
  не отбирает наборы с `&Изолированный(Уровень = "Процесс")` и стоит 1179 с вместо 62 с;
  скрипт сам собирает файлы по тегу, захардкоженного списка в нём нет.

  ⚠ **«Быстрый» почти не дешевле регрессии** — на замере 2026-08-07 он снимал 11 наборов
  из 140 и 166 тестов из 2783, то есть шесть процентов прогона. Тег `хаб` стоял тогда на 28 наборах, но 17 из них
  прогоняются всё равно: OneUnit 0.4.1 не передаёт фильтр тегов в изолированные наборы,
  а их в дереве большинство. Разметку не снимаем — она верна, и оба
  уровня подешевеют сами, когда апстрим научится видеть изолированные наборы. Разбор
  и замеры — в [ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md), текст issue —
  в [issues/ЧЕРНОВИК-ONEUNIT-теги-и-изоляция.md](issues/ЧЕРНОВИК-ONEUNIT-теги-и-изоляция.md).
- **Фикстуру подключает реестр, а не `ПодключитьСценарий` руками.** В наборе —
  `#Использовать "фикстуры"` рядом с `#Использовать asserts`, дальше
  `РеестрФикстур.Подключить("ИмяФикстуры")` по одной строке на фикстуру (так она ищется
  грепом). Продуктовые классы подключает `КлассыСлоя` — тоже идемпотентно. Голый
  `ПодключитьСценарий` в наборе — повод спросить «почему»: имена типов глобальны на процесс,
  и повторное подключение файла, чьи байты успели измениться, роняет **весь набор** до
  первого утверждения (разбор — [ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md), §2.1).
  Кодом закрыт случай, который реально стреляет: **ни один набор, делящий общий процесс
  прогона, голых подключений не содержит**. Оставшиеся голые подключения продуктовых
  классов живут в `&ПередВсеми` наборов с `&Изолированный(Уровень = "Процесс")`, где имя
  подключается ровно один раз на процесс, — там столкнуться не с чем.
- **⛔ Длинный прогон и правки дерева в одном чекауте несовместимы.** Регрессия читает
  файлы все тридцать минут: изолированные наборы стартуют дочерними процессами по ходу
  дела, а линты читают исходники в момент теста. Мерж или правка под работающим прогоном
  даёт «ошибочные наборы» и недосчитанные тесты — именно так был потерян прогон 2026-08-08.
  Регрессию гоняют там, где дерево не меняется, а числа принимают только от такого прогона.
- Доступ к данным — только через autumn-data; сырого SQL в проекте нет.
- Markdown-рендеринг — библиотека oscript-md (автор — владелец проекта), свою не писать.
- **Комментарии: код — лучший комментарий.** Шапка модуля — 1-2 строки о том, что конкретно
  в файле. Экспортные процедуры и функции документируются по стандарту 1С (назначение,
  `Параметры:`, `Возвращаемое значение:`) — только контракт, без ссылок на документацию,
  идентификаторов требований и истории решений. Конструкторы `ПриСозданииОбъекта`
  не документируются: их параметры — внедряемые ОСенью желуди. Неэкспортные методы —
  максимум одна строка на неочевидное поведение. Знание о дефектах чужих библиотек,
  принятых рисках и питфолах платформы живёт в [ЗНАНИЕ.md](docs/процесс/ЗНАНИЕ.md),
  а не в комментариях. Обратное направление — рабочее: требование называет классы
  и наборы в строке «Реализация», код о требовании не знает.

## Библиотеки-сателлиты

Правила создания библиотек-сателлитов:

- создаются в `/Users/e.ivanov/git_reps/public/<имя>` (рядом с этим проектом), отдельный
  git-репозиторий;
- обязательный состав: `packagedef` (semver, зависимости), `src/`, `tests/` (OneUnit),
  `README.md` (назначение, установка, примеры API), `LICENSE` (MIT), `.mcp.json`;
- имя — строчными буквами; API — русскоязычный; самодостаточны (не зависят от OpenHub);
- **все сателлиты опубликованы на hub.oscript.io** и приезжают оттуда: `vendor/`,
  локального файлового хаба и установки из `.ospx` в проекте больше нет;
- у каждого свой репозиторий на GitHub с парой workflow (`test.yaml` через
  `autumn-library/workflows`, `release.yaml` — публикация в хаб по GitHub-релизу).
  Новая версия попадает в хаб публикацией релиза, а не ручной сборкой;
- в `packagedef` OpenHub — обычная `.ЗависитОт("<имя>", "<версия>")`, версия та же,
  что опубликована.

⚠ **Сателлит, сузивший публичный интерфейс, ломает OpenHub молча.** За волну 2026-08-05
три библиотеки (`os-scheduler`, `html-sanitizer`, `jwt-verify`) убрали классы из
`lib.config` в `src/internal`, **не подняв версию**, — и хаб перестал стартовать
(`Новый Планировщик(...)` подхватывал чужой конструктор). Меняешь публичный состав —
поднимай версию и правь потребителя тем же заходом; берёшь зависимость на новую
версию — прогоняй смоук, а не только сборку.
